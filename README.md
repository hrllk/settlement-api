# 크리에이터 정산 API

온라인 강의 플랫폼의 크리에이터 정산 시스템. 판매·취소를 기록하고 기간별 정산을 계산한다.

Spring Boot 4.1.1 / Java 21 / H2 인메모리 / 헥사고날 아키텍처. **테스트 97건.**

> **먼저 읽을 것이 하나 있다.** 운영자 기간 집계는 **월별 정산의 합이 아니다.** creator-2의 1~3월이 운영자 조회에서 48,000원, 월별 조회 세 번의 합으로는 36,000원이다. 버그가 아니라 의도한 계산 방식이다. 근거는 [가정 1](#1-운영자-기간-집계는-월별-정산의-합이-아니다)에 있다.

## 실행

요구 환경: **Java 21**. Gradle은 설치하지 않아도 된다 (Wrapper 포함).

```bash
./gradlew bootRun     # http://localhost:8080
./gradlew test        # 97건
```

`build.gradle`의 toolchain이 21로 고정돼 있다. Java 17에서 돌리면 Gradle이 툴체인을 내려받으려다 실패하고, 실패 메시지에 원인이 안 드러난다.

**H2 콘솔** — http://localhost:8080/h2-console

| 항목 | 값 |
| --- | --- |
| JDBC URL | `jdbc:h2:mem:creator-settlement` |
| User | `sa` |
| Password | (없음) |

JDBC URL을 안 넣으면 콘솔 기본값 `jdbc:h2:~/test`로 접속해 빈 DB를 보게 된다.

인메모리라 **재시작하면 초기 데이터로 돌아간다.**

## API

액터는 헤더 두 개로 표기한다. `X-Actor-Id`, `X-Actor-Role`(`ADMIN` 또는 `CREATOR`).

| 메서드 | 경로 | ADMIN | CREATOR |
| --- | --- | --- | --- |
| POST | `/api/sales` | O | 403 |
| POST | `/api/sales/{saleId}/cancellations` | O | 403 |
| GET | `/api/creators/{creatorId}/sales?from=&to=` | 전부 | 본인만 |
| GET | `/api/creators/{creatorId}/settlements/{yearMonth}` | 전부 | 본인만 |
| GET | `/api/admin/settlements?from=&to=` | O | 403 |

**시각은 오프셋 포함 ISO-8601만 받는다.** `2025-03-05T10:00:00+09:00`. 오프셋이 없으면 400이다. 오프셋 없이 받으면 서버가 무슨 시간대로 읽었는지 요청만 보고 알 수 없고, Jackson이 UTC로 **조용히** 파싱해 9시간 어긋난 값이 아무 오류 없이 저장된다. 경계에 걸린 값은 귀속 월까지 바뀐다.

**`from`/`to`는 종료일 하루 전체를 포함한다.** `from=2025-03-01&to=2025-03-31`은 3월 31일을 포함한다. 내부적으로 `[03-01 00:00 KST, 04-01 00:00 KST)`로 바뀐다.

### 조회

```bash
# creator-1의 2025-03 정산
curl -s localhost:8080/api/creators/creator-1/settlements/2025-03 \
  -H 'X-Actor-Id: creator-1' -H 'X-Actor-Role: CREATOR'
```
```json
{"creatorId":"creator-1","yearMonth":"2025-03","grossSales":260000,"saleCount":4,
 "refunds":110000,"cancelCount":2,"netSales":150000,"fee":30000,"payout":120000}
```

```bash
# 운영자 기간 집계
curl -s 'localhost:8080/api/admin/settlements?from=2025-03-01&to=2025-03-31' \
  -H 'X-Actor-Id: admin-1' -H 'X-Actor-Role: ADMIN'
```
```json
{"from":"2025-03-01","to":"2025-03-31","creators":[
  {"creatorId":"creator-1","grossSales":260000,"saleCount":4,"refunds":110000,
   "cancelCount":2,"netSales":150000,"fee":30000,"payout":120000},
  {"creatorId":"creator-2","grossSales":60000,"saleCount":1,"refunds":0,
   "cancelCount":0,"netSales":60000,"fee":12000,"payout":48000},
  {"creatorId":"creator-3","grossSales":0,"saleCount":0,"refunds":0,
   "cancelCount":0,"netSales":0,"fee":0,"payout":0}],
 "totalPayout":168000}
```

실적 없는 creator-3도 0원으로 들어간다. 판매·취소 자료만 훑으면 그 존재를 알 방법이 없어 목록에서 통째로 빠진다.

```bash
# 판매 목록 — sale-5를 1월 구간으로 조회
curl -s 'localhost:8080/api/creators/creator-2/sales?from=2025-01-01&to=2025-01-31' \
  -H 'X-Actor-Id: creator-2' -H 'X-Actor-Role: CREATOR'
```
```json
{"creatorId":"creator-2","sales":[
  {"saleId":"sale-5","courseId":"course-3","amount":60000,
   "paidAt":"2025-01-31T23:30:00+09:00","refundStatus":"FULL"}]}
```

**`refundStatus`가 `FULL`인 것이 핵심이다.** 취소는 2월인데 1월 구간 조회에서도 `FULL`이다. [환불 상태만 기간과 무관하다](#환불-상태만-기간과-무관하다)를 보라.

### 등록

```bash
curl -s -X POST localhost:8080/api/sales \
  -H 'X-Actor-Id: admin-1' -H 'X-Actor-Role: ADMIN' -H 'Content-Type: application/json' \
  -d '{"courseId":"course-1","amount":50000,"paidAt":"2025-06-10T10:00:00+09:00"}'
```
```json
{"saleId":"250970b2-5529-489f-95de-47bd09d2c4ff","courseId":"course-1",
 "amount":50000,"paidAt":"2025-06-10T10:00:00+09:00"}
```

`saleId`는 서버가 만드는 UUID다. 시드의 `sale-1` 형태는 형식 제약이 아니다.

```bash
# 취소 등록
curl -s -X POST localhost:8080/api/sales/{saleId}/cancellations \
  -H 'X-Actor-Id: admin-1' -H 'X-Actor-Role: ADMIN' -H 'Content-Type: application/json' \
  -d '{"amount":30000,"cancelledAt":"2025-06-20T10:00:00+09:00"}'
```

### 오류

**모든 실패가 RFC 9457 Problem Details 한 가지 모양이다.** `Content-Type: application/problem+json`. 포맷을 발명하지 않고 Spring 내장 `ProblemDetail`을 쓴다.

```bash
# 누적 초과 환불 → 409
curl -s -X POST localhost:8080/api/sales/{saleId}/cancellations \
  -H 'X-Actor-Id: admin-1' -H 'X-Actor-Role: ADMIN' -H 'Content-Type: application/json' \
  -d '{"amount":60000,"cancelledAt":"2025-07-03T10:00:00+09:00"}'
```
```json
{"type":"urn:problem-type:refund-amount-exceeded","title":"Conflict","status":409,
 "detail":"refund exceeds sale amount: saleId=832244b6..., saleAmount=80000, alreadyCancelled=30000, requested=60000",
 "instance":"/api/sales/832244b6.../cancellations","code":"REFUND_AMOUNT_EXCEEDED"}
```

```bash
# 타인 정산 조회 → 403
curl -s localhost:8080/api/creators/creator-1/settlements/2025-03 \
  -H 'X-Actor-Id: creator-2' -H 'X-Actor-Role: CREATOR'
```
```json
{"type":"urn:problem-type:actor-access-denied","title":"Forbidden","status":403,
 "detail":"creator creator-2 cannot access creator creator-1",
 "instance":"/api/creators/creator-1/settlements/2025-03","code":"ACTOR_ACCESS_DENIED"}
```

`type`이 `urn:`인 것은 오류 문서 사이트를 호스팅하지 않기 때문이다. RFC 9457이 허용하는 형태다. `code`는 같은 값의 짧은 표기이며 클라이언트 분기용 확장 멤버다.

| `code` | status | 언제 |
| --- | ---: | --- |
| `SALE_NOT_FOUND` | 404 | 없는 판매에 취소 |
| `COURSE_NOT_FOUND` | 404 | 없는 강의로 판매 등록 |
| `REFUND_AMOUNT_EXCEEDED` | 409 | 누적 환불이 원결제액 초과 |
| `ACTOR_ACCESS_DENIED` | 403 | 타인 자원 또는 운영자 전용 |
| `INVALID_SETTLEMENT_PERIOD` | 400 | `2025-13`, 종료일 < 시작일 |
| `VALIDATION_FAILED` | 400 | 금액 0 이하, 필수 필드 누락 |
| `MALFORMED_REQUEST` | 400 | 오프셋 없는 시각 |
| `INVALID_ACTOR_HEADER` | 400 | 액터 헤더 누락·형식 오류 |
| `MISSING_PARAMETER` | 400 | `from` 또는 `to` 누락 |

**400과 403은 다른 경로다.** 400은 신원을 **모르는** 것이고 403은 신원을 **알고 거부**하는 것이다. 클라이언트가 재시도할지 포기할지 판단하는 근거가 된다.

**`code`가 붙는 것은 우리가 이름 붙인 실패뿐이다.** 405나 없는 경로처럼 프레임워크가 만드는 실패는 `application/problem+json`이지만 `code`와 `type`이 없다.

```json
{"detail":"Method 'PATCH' is not supported.","instance":"/api/sales",
 "status":405,"title":"Method Not Allowed"}
```

거기에 `code`를 붙이려면 Spring의 프레임워크 예외 목록을 우리가 복제해야 하고, 그 목록은 버전마다 바뀐다.

## 데이터 모델

설계 결정 10건과 근거는 [`docs/persistence-decisions.md`](docs/persistence-decisions.md)에 있다. 여기서는 데이터 모델만 추린다.

```text
creators (id, name)
    ▲ creator_id
courses  (id, creator_id, title)
    ▲ course_id
sales    (id, course_id, amount, paid_at)      idx (course_id, paid_at)
    ▲ sale_id
cancels  (id, sale_id, amount, cancelled_at)   idx (sale_id, cancelled_at)
```

**판매는 크리에이터를 직접 갖지 않는다.** 강의를 거쳐 안다. 비정규화하면 조인이 사라지지만 강의 소유자가 바뀔 때 판매 행 전부를 같이 고쳐야 하고, 안 고치면 **과거 정산이 조용히 틀어진다.** 7건 규모에서 조인 비용이 0이라 정규화를 택했다.

**환불 상태 컬럼이 없다.** 취소 합계에서 매번 계산한다. 저장하면 취소가 하나 더 들어올 때 갱신을 빠뜨리는 경로가 생긴다.

**FK 제약을 걸지 않았다.** 없는 강의로 판매를 등록하는 것은 애플리케이션이 `CourseNotFound` 404로 막는다. DB 제약에 맡기면 `DataIntegrityViolationException`이 500으로 새어 나간다.

### 초기 데이터 17행

크리에이터 3 + 강의 4 + 판매 7 + 취소 3.

| 판매 | 강의 | 크리에이터 | 금액 | 결제 (KST) |
| --- | --- | --- | ---: | --- |
| sale-1 | course-1 | creator-1 | 50,000 | 2025-03-05 10:00 |
| sale-2 | course-1 | creator-1 | 50,000 | 2025-03-15 14:30 |
| sale-3 | course-2 | creator-1 | 80,000 | 2025-03-20 09:00 |
| sale-4 | course-2 | creator-1 | 80,000 | 2025-03-22 11:00 |
| sale-5 | course-3 | creator-2 | 60,000 | **2025-01-31 23:30** |
| sale-6 | course-3 | creator-2 | 60,000 | 2025-03-10 16:00 |
| sale-7 | course-4 | creator-3 | 120,000 | 2025-02-14 10:00 |

| 취소 | 원본 | 금액 | 취소 (KST) | 구분 |
| --- | --- | ---: | --- | --- |
| cancel-1 | sale-3 | 80,000 | 2025-03-25 10:00 | 전액 |
| cancel-2 | sale-4 | 30,000 | 2025-03-26 10:00 | 부분 |
| cancel-3 | sale-5 | 60,000 | **2025-02-03 10:00** | 전액, 월 경계 |

굵은 두 행이 월 경계 시나리오다. `sale-5`는 KST 1월 마지막 날 23:30 결제(UTC로는 `2025-01-31T14:30Z`)이고 취소는 2월이다. **판매는 1월, 환불은 2월에 귀속된다.**

**취소 초기 데이터는 원본 과제에 없어 직접 정의했다.** 금액과 귀속 월은 과제 서술("3월 취소", "2월 초 취소")에서 가져오고, 구체 시각은 10:00 KST로 고정했다. 자정과 자정 직전에서 멀어 어떤 구간 구현에서도 귀속 월이 흔들리지 않는다. 경계 검증은 단위 테스트 픽스처가 따로 세 방향으로 잠갔다.

### 기대 정산

| 크리에이터 | 월 | 총 판매(건) | 환불(건) | 순 판매 | 수수료 | 정산 예정 |
| --- | --- | --- | --- | ---: | ---: | ---: |
| creator-1 | 2025-03 | 260,000 (4) | 110,000 (2) | 150,000 | 30,000 | 120,000 |
| creator-2 | 2025-01 | 60,000 (1) | 0 (0) | 60,000 | 12,000 | 48,000 |
| creator-2 | 2025-02 | 0 (0) | 60,000 (1) | −60,000 | **0** | **−60,000** |
| creator-2 | 2025-03 | 60,000 (1) | 0 (0) | 60,000 | 12,000 | 48,000 |
| creator-3 | 2025-02 | 120,000 (1) | 0 (0) | 120,000 | 24,000 | 96,000 |
| creator-3 | 2025-03 | 0 (0) | 0 (0) | 0 | 0 | 0 |

**creator-2의 2025-02가 이 표에서 가장 설명이 필요한 행이다.** 판매 없이 1월 판매분의 취소만 있어 순 판매액이 음수다. 수수료는 0으로 막고 정산 예정액은 음수를 그대로 둔다. 근거는 [가정 5](#계산-정책-57).

**식별자를 `String`으로 뒀다.** `CreatorId` 같은 타입 래퍼를 만들면 타입 안전성은 오르지만 클래스와 변환 코드가 늘어난다. 원본 데이터의 식별자가 `creator-1` 같은 문자열이라 래핑 이득도 작다.

**인덱스 컬럼 순서를 뒤집지 않았다.** `(course_id, paid_at)`, `(sale_id, cancelled_at)`을 유지했다. 뒤집자는 검토가 있었으나 **두 조회 경로가 상반된 선행 컬럼을 원한다** — 특히 `findCancelsBySaleIds`는 시간 조건이 아예 없어 `sale_id` 선행이 필요하고, `(cancelled_at, sale_id)`로 두면 풀스캔이 된다. 7건 규모에서 실측 차이가 0이라 하나만 두고 관찰을 남긴다.

## KST 경계와 이중 집계

### 반열린 구간

```text
2025-03 → [2025-03-01 00:00 KST, 2025-04-01 00:00 KST)
        = [2025-02-28 15:00 Z,   2025-03-31 15:00 Z)
```

시작은 포함, 끝은 배제다.

**원본 과제의 `말일 23:59:59`를 의도적으로 이탈했다.** 그 표현은 `23:59:59.001`부터 `23:59:59.999`까지 1초 미만 구간을 통째로 누락한다. 밀리초 정밀도로 저장하는 시스템에서 그 사이에 결제가 들어오면 **어느 달에도 안 잡힌다.**

반열린 구간은 인접한 달이 빈틈도 겹침도 없이 이어진다. 2월의 끝과 3월의 시작이 같은 순간이고, 그 순간은 3월에만 속한다.

**일자 구간은 사용자 표기와 다르다.** `from`/`to`는 양끝 포함으로 받아서 반열린 구간으로 바꾼다.

```text
?from=2025-03-01&to=2025-03-31
  → [2025-03-01 00:00 KST, 2025-04-01 00:00 KST)
                            ^ 종료일 + 1일
```

응답의 `to`는 요청 문자열을 그대로 되돌려준 것이지 내부의 `toExclusive`가 아니다.

### 저장은 `Instant`, 해석은 KST

DB에는 UTC 순간을 저장한다. KST 연월·일자를 `Instant` 구간으로 바꾸는 책임은 `SettlementPeriod` **한 클래스에만** 있다. 계산기와 어댑터는 시간대를 모른다.

**`LocalDateTime`을 쓰지 않았다.** 값이 KST인지 UTC인지 코드에 안 남아, `sale-5`가 1월 대신 2월로 귀속되는 사고의 전형적 원인이다.

`sale-5`가 이 프로젝트에서 유일하게 KST와 UTC의 날짜가 갈리는 레코드다. KST 1월 구간은 `[2024-12-31T15:00Z, 2025-01-31T15:00Z)`이고 `14:30Z`는 그 안에 **30분 남기고** 들어간다.

### 이중 집계 기준

**판매는 `paidAt`, 환불은 `cancelledAt`으로 각각 귀속 기간을 판단한다.**

| | 기준 컬럼 |
| --- | --- |
| 총 판매액, 판매 건수 | `paidAt` |
| 환불액, 취소 건수 | `cancelledAt` |

**금액뿐 아니라 건수도 같은 기준을 따른다.** creator-2의 2025-02는 판매 건수 0, 취소 건수 1이다. 판매가 없는데 취소만 있는 달이 실재한다. 그래서 응답에 판매 건수와 취소 건수를 따로 담는다 — 하나로 합치면 이 달이 "1건"으로 보여 판매가 있었는지 알 수 없다.

### 환불 상태만 기간과 무관하다

집계 금액은 기간으로 나뉘지만 **판매별 환불 상태는 나뉘지 않는다.** 그 판매에 연결된 **모든** 취소를 본다.

`sale-5`를 1월 판매 목록으로 조회하면 환불 상태가 `FULL`이다. 취소는 2월이지만 상태는 **판매의 속성**이지 기간의 속성이 아니다. 1월 창으로 취소를 조회하면 `cancel-3`이 안 잡혀 `NONE`이 나오는데, 그건 틀린 답이다.

**금액은 기간으로 자르고, 상태는 안 자른다.** 이 구분이 이 프로젝트에서 가장 헷갈리는 지점이다.

## 가정과 이탈 근거

### 1. 운영자 기간 집계는 월별 정산의 합이 아니다

**이것만 놓치면 나머지 20항이 다 있어도 감점된다.**

기간 전체를 **단일 정산 구간**으로 계산한다. 월별로 계산해 더하지 않는다.

```text
단일 구간 (채택):  (60,000 + 60,000) − 60,000 = 60,000  → 수수료 12,000 → 48,000

월별 합산:   1월  60,000 − 0      =  60,000 → 수수료 12,000 →  48,000
             2월       0 − 60,000 = −60,000 → 수수료      0 → −60,000
             3월  60,000 − 0      =  60,000 → 수수료 12,000 →  48,000
                                                        합계     36,000
```

12,000원 차이는 월별 합산일 때 2월의 음수 순 판매액에 **수수료 0원 제한**이 걸려 1월에 이미 뗀 수수료가 상쇄되지 않기 때문이다. 기간 전체로 보면 1월 매출과 2월 환불이 먼저 상쇄되고 남은 60,000에만 수수료가 붙는다.

전체 합계로는 단일 구간 **264,000**, 월별 합산 252,000이다.

**월별 합산을 안 쓰는 이유.** 음수 월마다 제한이 반복 적용되어 크리에이터에게 불리하고, "왜 월별 합과 다른가"를 설명할 수 없다. 단일 구간은 계산기를 기간만 바꿔 그대로 재사용하므로 순수 계산기 설계와도 맞는다.

월별 조회와 운영자 집계가 `SettlementQuery` **한 곳**을 쓴다. 두 경로의 차이가 기간 하나뿐이라는 것을 구조로 보장한다.

**문서 없이 이 동작을 보면 버그다.** 이 절의 존재 이유가 그것이다.

### 원본 과제 이탈 (2~4)

**2. 반열린 구간 채택.** `말일 23:59:59`는 1초 미만 구간을 누락한다.

**3. 초과 환불 거부 규칙 추가.** 원본에 없다. 누적 합계가 원결제액을 넘으면 409. 판정은 `Sale` 애그리게이트가 소유해 `cancel()`을 부르는 어떤 경로도 우회할 수 없다. 뺄셈으로 비교한다 — `already + amount`로 쓰면 `@Positive`가 허용하는 `Long.MAX_VALUE`가 오버플로해 음수가 되고 상한 검사를 그냥 통과한다.

**4. 취소 초기 데이터를 직접 정의.** 금액·귀속월은 과제 서술에서, 시각은 10:00 KST로 고정.

### 계산 정책 (5~7)

**5. 수수료는 0으로 막고 정산 예정액은 음수를 허용한다.** 둘은 같은 종류의 수가 아니다. 수수료는 플랫폼이 **매출에 부과하는** 값이라 매출이 음수면 부과할 대상이 없다. 정산 예정액은 실제 **채권·채무**라 음수가 "크리에이터가 돌려줄 금액"이라는 의미를 갖는다. 응답에서 0으로 깎거나 절댓값을 취하지 않는다.

**6. 금액은 원 단위 `long`이고 수수료는 버림이다.** 양수 구간에서 `long` 나눗셈의 절단이 곧 버림이다. 순 판매액 33,333원이면 수수료 6,666원(실제 6,666.6).

**7. 빈 월은 404가 아니라 200 + 전 항목 0이다.** 404로 두면 "정산이 없다"와 "크리에이터가 없다"를 클라이언트가 구분할 수 없다. **없는 크리에이터를 조회해도 같다.** 조회 두 엔드포인트가 같은 규칙을 쓴다. 등록은 다르다 — `courseExists`로 404를 낸다. 기준이 다른 것이 아니라 **쓰기와 조회의 위험이 다르다.** 없는 강의로 판매를 넣으면 어떤 크리에이터에도 속하지 않는 유령 행이 영구히 남고, 없는 크리에이터를 조회하면 0이 나오고 끝이다.

### 접근 경계 (8~10)

**8. 액터 헤더는 실제 인증이 아니다.** `X-Actor-Role: ADMIN`이라고 쓰면 그냥 운영자가 된다. 토큰도 서명도 검증하지 않는다. 과제가 명시적으로 허용한 단순화다. 위조하지 않은 클라이언트까지 통과시킬 이유는 없어 역할 판정은 그대로 건다.

**9. 판매·취소 등록을 ADMIN으로 제한했다.** 원본에 명시가 없다. 크리에이터가 자기 강의의 판매를 임의로 등록할 수 있으면 **정산을 스스로 부풀릴 수 있다.** 등록은 결제 시스템이 하는 일이라고 봤다.

**10. 오류 포맷은 RFC 9457이고 `RefundAmountExceeded`는 409다.** 포맷을 발명하지 않고 Spring 내장 `ProblemDetail`을 쓴다. 409를 고른 것은 요청 형식이 아니라 **자원 상태와의 충돌**이기 때문이다 — 400으로 두면 Bean Validation 실패와 구분되지 않는다.

### 검증하지 않는 것 (11~14)

**11. 취소 동시성을 보장하지 않는다.** 같은 판매에 취소 두 건이 동시에 오면 각자 같은 상태를 읽고 각자 합계 검사를 통과할 수 있다. 잔여 50,000원에 40,000원짜리 두 건이 동시에 오면 합계 80,000원이 원결제를 넘긴다. **규칙이 도메인에 있다는 것과 원자적으로 적용된다는 것은 다른 문제다.** 실무라면 판매 행에 `@Version`을 두거나 `SELECT ... FOR UPDATE`로 막을 지점이다.

**12. 취소 시각이 결제 시각보다 이른 경우를 검증하지 않는다.** 과거로 소급된 취소가 들어갈 수 있다.

**13. ADMIN이 임의의 `paidAt`으로 과거 판매를 등록할 수 있다.** 시드 재현에 필요하지만, 이미 마감된 달의 정산을 사후에 바꿀 수 있다는 뜻이다.

**14. 조회 기간 길이에 상한이 없다.** 10년 구간도 받는다. 운영자 집계는 페이지네이션도 없다.

그 밖에 과제 범위라 막지 않은 것들 — 로그에 식별자를 그대로 남기므로 개행이 든 `creatorId`로 로그 줄을 위조할 수 있고, 요청 본문 크기 제한과 호출 빈도 제한이 없다. 실서비스면 각각 로그 이스케이프, `server.max-http-request-header-size`, 게이트웨이 레벨 제한으로 다룰 지점이다.

### 설계 선택 (15~18)

**15. 집계를 DB로 내리지 않고 순수 계산기를 택했다.** `SettlementCalculator`는 (기간, 판매, 취소)의 순수 함수라 Spring도 H2도 없이 42건이 돈다. 기간이 길면 해당 구간 자료가 전부 메모리에 올라온다. 7건 기준에서 문제없고 설명 가능성을 우선했다.

**16. 운영자 집계가 크리에이터마다 포트를 부른다 (N+1).** 3명이면 조회 7회다. 포트 계약을 "`creatorId` 항상 필수"로 단순하게 유지하기 위한 선택이다. 크리에이터가 수천 명이면 다시 볼 지점이다.

**17. 인덱스 컬럼 순서에서 두 조회 경로가 상반된 선행 컬럼을 원한다.** `findCancelsBySaleIds`는 시간 조건이 없어 `sale_id` 선행이 필요하다.

**18. 식별자를 타입 래퍼 없이 `String`으로 뒀다.** 새 판매 ID는 서버 생성 UUID이며 시드의 `sale-1` 형태는 형식 제약이 아니다.

### 운영 관점 (19~20)

**19. `ddl-auto=create-drop`은 기동할 때마다 스키마를 새로 만든다.** 인메모리 H2 전용이며 운영 DB에 그대로 쓰면 데이터가 사라진다.

**20. H2 콘솔이 인증 없이 `/h2-console`에 열려 있다.** 채점 편의를 위한 설정이다. 운영 프로파일에서는 반드시 꺼야 한다.

### 검증 (21)

**21. 커버리지 감사.** 테스트가 여섯 Task에 흩어져 있어 표가 없으면 커버리지를 한눈에 볼 수 없다. 시나리오 28행이 각각 어느 파일의 어느 메서드로 검증되는지 [`docs/coverage-audit.md`](docs/coverage-audit.md)에 대조해 뒀다. **빈 행 없다.**

| --- | --- |
| 반열린 구간 경계 3방향 | 시작 포함 / 말일 23:59:59.999 포함 / 다음 달 1일 00:00 배제. `<=`를 쓰면 셋째가, `<`를 시작에 쓰면 첫째가 깨진다 |

| 항목 | 왜 |
| --- | --- |
| 정산 상태 전이 (대기·확정·지급) | 과제 명시적 제외 |
| CSV 내보내기 | 과제 명시적 제외 |
| 수수료율 이력 테이블 | 인터페이스 뒤에 두는 것까지만 |
| Docker | 과제 명시적 제외 |
| 크리에이터·강의 관리 API | 과제 명시적 제외. 시드로만 존재 |
| 정교한 인증·인가 | 과제가 헤더 방식을 허용 |
| 광범위한 테스트 커버리지 | 핵심 판단 시나리오에 집중 |

**수수료율은 인터페이스까지만 했다.** `FeePolicy` + `FixedRateFeePolicy(2000bp)`로 요율을 교체 가능하게 뒀다. 요율 값은 도메인이 갖지 않는다 — `application.yml`의 `settlement.fee.basis-points`가 원본이고 `DomainConfig`가 주입한다. 바꾸려면 설정 한 줄이다.

시점별 요율(1월은 20%, 2월부터 15%)이 필요해지면 `FeePolicy`에 기간 인자를 넣고 구현체를 하나 더 만든다. **계산기는 안 바뀐다.**

**정산 상태 전이를 붙이려면.** `SettlementSummary`는 영속화되지 않는 값 타입이다. 매 조회마다 원본 자료에서 다시 계산한다. 상태 전이를 붙이려면 정산 스냅샷 엔티티를 새로 두고 계산 결과를 그 시점에 고정하면 된다. 계산기는 그대로 두고 스냅샷을 만드는 유스케이스와 상태 컬럼을 가진 엔티티가 추가된다. **기존 구조를 뜯을 필요가 없다.**

**규모가 커지면 세 가지가 순서대로 문제가 된다.**

1. **크리에이터 수** — 운영자 집계가 크리에이터마다 포트를 부른다. 수백 명이면 배치 조회로 바꾼다.
2. **기간 길이** — 순수 계산기가 구간의 판매·취소를 전부 메모리에 올린다. 상한을 두거나 집계를 DB로 내린다.
3. **인덱스** — 두 조회 경로가 상반된 선행 컬럼을 원한다. 트래픽이 생기면 인덱스를 하나 더 두거나 커버링 인덱스를 검토한다.

지금 안 한 이유는 "몰라서"가 아니라 "규모가 아니어서"다.

### 교차 검토로 잡은 것

서로 다른 모델로 같은 문서를 두 번 검토했다. "AI를 썼다"보다 **"AI로 무엇을 잡았다"**가 정보량이 크다.

- **쓰기 어댑터 부재.** Task 2가 만드는 포트는 조회 4개뿐인데 Task 4는 저장과 ID 조회가 필요했다. 11개 섹션 검수가 놓친 구현 블로커였다.
- **순환 의존.** Task 4가 Task 5의 접근 정책을 호출하는데 Task 5는 Task 4의 전역 예외 처리기를 의존했다.
- **헥사고날 방향 역전.** 유스케이스가 `ActorContext`를 받으면서 `application → adapter.in` 의존이 생겼다. 액터 타입을 `application.actor`로 옮기고 해석기만 어댑터에 남겼다.
- **테스트 소유권 중복.** 같은 시나리오를 두 Task가 각자 단언하고 있었다.
- **Boot 4 모듈 분할.** `@DataJpaTest`·`@AutoConfigureMockMvc`가 `spring-boot-test-autoconfigure` jar에 없다. jar를 열어 확인했다. 모르고 갔으면 컴파일 오류로 시간을 태웠을 항목이다.

### 사람이 판단한 것

- **운영자 집계를 단일 구간으로 할지 월별 합산으로 할지**는 정책 판단이라 사람이 정했다.
- 인덱스 컬럼 순서를 뒤집자는 AI 제안을 **철회**했다. 두 조회 경로가 상반된 선행 컬럼을 원한다는 것이 뒤늦게 드러났다.
- 영속성을 MyBatis로 바꿀지 검토하고 **JPA를 유지**하기로 했다. 쓰는 JPA 기능이 사실상 없어 바꿔도 얻는 것이 적고, 질문의 종류만 바뀐다.
- 범위 확장 제안을 3시간 예산 기준으로 반려했다.

### 검산과 실행 검증에 썼다

시드 17행이 기대 정산표를 재현하는지 계산으로 검산했다. 손으로 하면 6개 행 × 7개 값이라 실수가 난다. **운영자 1~3월이 월별 합(252,000)이 아니라 264,000이라는 것도 이 검산에서 확인했다.**

구현 후에는 애플리케이션을 띄워 이 README의 curl을 전부 실행하고 응답을 대조했다. **여기 실린 JSON은 전부 실제 응답이다.**

### 한계

AI가 만든 첫 계획에는 순환 의존과 소유권 중복이 있었다. 문서를 각각 보면 완결돼 보였고 **세트로 놓고 봐야 드러났다.**

명세도 두 번 틀렸다. "`@Transactional`을 다르게 쓰면 Spring 컨텍스트가 늘어난다"와 "`to` 규칙은 테스트로 구분할 수 없다" 둘 다 **실제로 돌려보니 사실이 아니었다.** 컨텍스트 식별자를 찍어 보고, 하루짜리 구간을 만들어 보고 나서야 알았다.

**그럴듯한 문장과 사실을 가르는 것은 실행뿐이다.** 검토 없이 받았으면 구현 중에 막혔거나, 틀린 근거를 문서에 실었을 것이다.
