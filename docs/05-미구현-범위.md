## 요구사항 위반

**이상 미만 구간 채택.** `말일 23:59:59`는 1초 미만 구간을 누락합니다 — [01](01-정산-규칙과-KST-경계.md#이상-미만-구간).

**초과 환불 거부 규칙 추가.** 원본에 없습니다. 누적 합계가 원결제액을 넘으면 409입니다. 판정은 `Sale` 애그리게이트가 소유해 어떤 경로도 우회할 수 없습니다.

**취소 초기 데이터를 직접 정의.** 금액·귀속월은 과제 서술에서, 시각은 10:00 KST로 고정했습니다.

## 보장하지 않는 것

**취소 동시성.** 같은 판매에 취소 두 건이 동시에 오면 각자 같은 상태를 읽고 각자 검사를 통과합니다. **규칙이 도메인에 있다는 것과 원자적으로 적용된다는 것은 다릅니다.**

실측으로 재현했습니다. 80,000원 판매(기존 취소 30,000원)에 40,000원 취소를 동시에 두 건 넣으면 둘 다 201이고 누적 110,000원이 됩니다.

막으려면 판매 행을 `SELECT ... FOR UPDATE`로 잠가야 합니다. **`@Version` 낙관적 락은 이 구조에서 듣지 않습니다** — 충돌하는 쓰기가 `sales` UPDATE가 아니라 `cancels` INSERT라 부모 행 버전이 오르지 않습니다.

**미래 시각.** `paidAt`·`cancelledAt`이 현재보다 뒤여도 받습니다. 결제 이전 취소는 409로 거부하지만 미래 방향에는 기준 시각이 없습니다.

**마감된 달의 사후 변경.** ADMIN이 임의의 `paidAt`으로 과거 판매를 등록할 수 있습니다. 초기 데이터 재현에 필요하지만, 이미 조회된 정산이 나중에 달라진다는 뜻입니다.

**조회 기간 상한.** 10년 구간도 받고 페이지네이션도 없습니다.

그 밖에 막지 않은 것들입니다. 로그에 식별자를 그대로 남겨 개행이 든 `creatorId`로 로그 줄을 위조할 수 있고, 요청 본문 크기와 호출 빈도 제한이 없습니다. 실서비스라면 로그 이스케이프, `max-http-request-header-size`, 게이트웨이 제한으로 다룰 지점입니다.

## 접근 경계의 한계

**액터 헤더는 실제 인증이 아닙니다.** `X-Actor-Role: ADMIN`이라고 쓰면 그냥 운영자가 됩니다. 토큰도 서명도 검증하지 않습니다. 과제가 명시적으로 허용한 단순화입니다.

**판매·취소 등록을 ADMIN으로 제한했습니다.** 원본에 명시가 없습니다.

**구매 주체와 호출 주체가 다릅니다.** 판매를 발생시키는 사람은 수강생이고 요청 본문의 `studentId`에 담깁니다. 이 API를 *호출하는* 쪽은 결제 시스템입니다 — 과제가 "실제 결제 시스템 연동 불필요"라고 했으므로 ADMIN이 그 대역을 맡습니다.

크리에이터를 배제한 이유는 따로 있습니다. 자기 강의의 판매를 임의로 등록할 수 있으면 **정산을 스스로 부풀릴 수 있습니다.** 실제 서비스라면 결제 게이트웨이용 서비스 계정이나 서명된 웹훅으로 분리할 지점입니다.

**초과 환불은 409입니다.** 요청 형식이 아니라 **자원 상태와의 충돌**이기 때문입니다. 400으로 두면 Bean Validation 실패와 구분되지 않습니다.

## 운영에 쓸 수 없는 설정

**`ddl-auto=create-drop`** — 기동할 때마다 스키마를 새로 만듭니다. 운영 DB에 그대로 쓰면 데이터가 사라집니다.

**H2 콘솔이 인증 없이 `/h2-console`에 열려 있습니다.** 채점 편의를 위한 설정이며 운영 프로파일에서는 반드시 꺼야 합니다.

## 만들지 않은 기능

앞의 넷은 과제가 **선택 구현(추가 점수)**으로 제시한 항목입니다. 하지 않기로 한 것이지 과제가 제외한 것이 아닙니다.

| 항목 | 분류 | 왜 |
| --- | --- | --- |
| 정산 확정 상태 (PENDING → CONFIRMED → PAID) | 선택 구현 | 설계만. 아래 참조 |
| 동일 기간 중복 정산 방지 | 선택 구현 | 확정 상태와 한 몸입니다 |
| CSV·엑셀 다운로드 | 선택 구현 | 직렬화 층이라 계산기는 안 바뀝니다 |
| 수수료율 변경 이력 | 선택 구현 | `FeePolicy` 인터페이스까지 |
| 크리에이터·강의 관리 API | 요구사항에 없음 | 초기 데이터로만 존재합니다 |
| Docker | 요구사항에 없음 | `./gradlew bootRun` 하나로 뜹니다 |
| 정교한 인증·인가 | 과제가 허용 | "인증은 간략 처리 가능" |

**수수료율은 인터페이스까지 했습니다.** 요율 값은 도메인이 갖지 않습니다 — `application.yml`의 `settlement.fee.basis-points`가 원본이고 `DomainConfig`가 주입합니다. 바꾸려면 설정 한 줄입니다. 시점별 요율이 필요해지면 `FeePolicy`에 기간 인자를 넣고 구현체를 하나 더 만듭니다. **계산기는 바뀌지 않습니다.**

## 정산 확정 상태를 붙인다면

`PENDING → CONFIRMED → PAID`를 붙일 대상이 지금은 없습니다. 정산은 **매 조회마다 원본에서 다시 계산하는 무상태 값**이라 `SettlementSummary`가 영속화되지 않습니다. 상태는 어떤 레코드의 상태인데 그 레코드가 없습니다.

그래서 순서가 이렇습니다. **먼저 스냅샷을 만들고, 그 위에 상태를 얹습니다.**

```text
settlements
  id, creator_id, year_month,
  gross_sales, refunds, net_sales, fee, payout,   ← 확정 시점의 값을 고정
  status,                                          PENDING · CONFIRMED · PAID
  confirmed_at, paid_at
  UNIQUE (creator_id, year_month)
```

`UNIQUE (creator_id, year_month)`가 같은 달을 두 번 확정하는 것을 DB에서 막아, **동일 기간 중복 정산 방지가 여기서 같이 해결됩니다.** 확정 유스케이스는 `SettlementQuery.summarize`를 불러 값을 얻고 스냅샷으로 저장할 뿐이라 **계산기는 바뀌지 않습니다.**

### 붙이기 전에 답해야 하는 것

구현하지 않은 진짜 이유는 시간이 아니라 이 셋입니다.

1. **확정 후 과거 판매가 들어오면 어느 쪽이 맞습니까.** 스냅샷은 그대로고 실시간 계산은 바뀌어 두 값이 갈립니다. 확정의 존재 이유이기도 하지만, 이 시스템의 강점인 "언제 조회해도 같은 값"과 정면으로 부딪힙니다.
2. **월별 조회 API는 무엇을 보여줍니까.** 확정 전은 실시간, 확정 후는 스냅샷이면 같은 URL이 시점에 따라 다른 의미를 갖습니다.
3. **운영자 기간 집계와 단위가 다릅니다.** 확정은 월 단위인데 기간 집계는 임의 구간입니다. `2025-01-15 ~ 2025-03-20`을 확정할 수는 없습니다.

**셋 다 정책 판단이고 코드보다 먼저 정해야 합니다.** 답 없이 상태 기계만 넣으면 전이는 되는데 그래서 무엇이 달라지는지 설명할 수 없습니다.

### 규모가 커지면

1. **크리에이터 수** — 조회 횟수는 이미 상수지만 응답이 전체를 한 번에 돌려줍니다. 수백 명이면 페이지네이션이 필요합니다.
2. **기간 길이** — 순수 계산기가 구간의 판매·취소를 전부 메모리에 올립니다. 상한을 두거나 집계를 DB로 내립니다.
3. **인덱스** — 두 조회 경로가 상반된 선행 컬럼을 원합니다. 트래픽이 생기면 인덱스를 더 두거나 커버링 인덱스를 검토합니다.

지금 하지 않은 이유는 "몰라서"가 아니라 **"규모가 아니어서"**입니다.
