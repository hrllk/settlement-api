## 원본 과제 이탈 (2~4)

**2. 반열린 구간 채택.** `말일 23:59:59`는 1초 미만 구간을 누락합니다.

**3. 초과 환불 거부 규칙 추가.** 원본에 없습니다. 누적 합계가 원결제액을 넘으면 409입니다.
판정은 `Sale` 애그리게이트가 소유해 `cancel()`을 부르는 어떤 경로도 우회할 수 없습니다.
뺄셈으로 비교합니다. `already + amount`로 쓰면 `@Positive`가 허용하는 `Long.MAX_VALUE`가
오버플로해 음수가 되고 상한 검사를 그냥 통과합니다.

**4. 취소 초기 데이터를 직접 정의.** 금액·귀속월은 과제 서술에서, 시각은 10:00 KST로
고정했습니다.

## 조회 정책 (7)

**7. 빈 월은 404가 아니라 200 + 전 항목 0입니다.** 404로 두면 "정산이 없다"와 "크리에이터가
없다"를 클라이언트가 구분할 수 없습니다. 없는 크리에이터를 조회해도 같습니다.

등록은 다릅니다. `courseExists`로 404를 냅니다. 기준이 다른 것이 아니라 **쓰기와 조회의
위험이 다릅니다.** 없는 강의로 판매를 넣으면 어떤 크리에이터에도 속하지 않는 유령 행이
영구히 남고, 없는 크리에이터를 조회하면 0이 나오고 끝입니다.

## 접근 경계 (8~10)

**8. 액터 헤더는 실제 인증이 아닙니다.** `X-Actor-Role: ADMIN`이라고 쓰면 그냥 운영자가
됩니다. 토큰도 서명도 검증하지 않습니다. 과제가 명시적으로 허용한 단순화입니다. 위조하지
않은 클라이언트까지 통과시킬 이유는 없어 역할 판정은 그대로 겁니다.

**9. 판매·취소 등록을 ADMIN으로 제한했습니다.** 원본에 명시가 없습니다. 크리에이터가 자기
강의의 판매를 임의로 등록할 수 있으면 **정산을 스스로 부풀릴 수 있습니다.** 등록은 결제
시스템이 하는 일이라고 봤습니다.

**10. 오류 포맷은 RFC 9457이고 초과 환불은 409입니다.** 포맷을 발명하지 않고 Spring 내장
`ProblemDetail`을 씁니다. 409를 고른 것은 요청 형식이 아니라 **자원 상태와의 충돌**이기
때문입니다. 400으로 두면 Bean Validation 실패와 구분되지 않습니다.

## 검증하지 않는 것 (11~14)

**11. 취소 동시성을 보장하지 않습니다.** 같은 판매에 취소 두 건이 동시에 오면 각자 같은
상태를 읽고 각자 합계 검사를 통과할 수 있습니다. **규칙이 도메인에 있다는 것과 원자적으로
적용된다는 것은 다른 문제입니다.**

**실측으로 재현했습니다.** 80,000원 판매(기존 취소 30,000원)에 40,000원 취소를 동시에 두 건
넣으면 둘 다 201이고 누적 110,000원이 됩니다.

막으려면 판매 행을 `SELECT ... FOR UPDATE`로 잠가야 합니다. **`@Version` 낙관적 락은 이
구조에서 듣지 않습니다.** 충돌하는 쓰기가 `sales` UPDATE가 아니라 `cancels` INSERT라 부모
행 버전이 오르지 않고, 어댑터가 로드한 엔티티 대신 같은 값의 새 엔티티를 merge해 dirty
check도 UPDATE를 내지 않기 때문입니다.

**12. 미래 시각을 막지 않습니다.** `paidAt`·`cancelledAt`이 현재보다 뒤여도 받습니다. 결제
이전 취소는 409 `CANCEL_BEFORE_PAYMENT`로 거부하지만, 미래 방향에는 기준 시각이 없어
열어 뒀습니다.

**13. ADMIN이 임의의 `paidAt`으로 과거 판매를 등록할 수 있습니다.** 시드 재현에 필요하지만,
이미 마감된 달의 정산을 사후에 바꿀 수 있다는 뜻입니다.

**14. 조회 기간 길이에 상한이 없습니다.** 10년 구간도 받습니다. 운영자 집계는 페이지네이션도
없습니다.

그 밖에 과제 범위라 막지 않은 것들입니다. 로그에 식별자를 그대로 남기므로 개행이 든
`creatorId`로 로그 줄을 위조할 수 있고, 요청 본문 크기 제한과 호출 빈도 제한이 없습니다.
실서비스라면 각각 로그 이스케이프, `server.max-http-request-header-size`, 게이트웨이 레벨
제한으로 다룰 지점입니다.

## 설계 선택 (15~18)

**15. 집계를 DB로 내리지 않고 순수 계산기를 택했습니다.** `SettlementCalculator`는 (기간,
판매, 취소)의 순수 함수라 Spring도 H2도 없이 돕니다. 기간이 길면 해당 구간 자료가 전부
메모리에 올라옵니다. 7건 기준에서 문제없고 설명 가능성을 우선했습니다.

**16. 운영자 집계가 크리에이터마다 포트를 부릅니다(N+1).** 3명이면 조회 7회입니다. 포트
계약을 "`creatorId` 항상 필수"로 단순하게 유지하기 위한 선택입니다. 크리에이터가 수천
명이면 다시 볼 지점입니다.

**17. 두 조회 경로가 상반된 인덱스 선행 컬럼을 원합니다.** `findCancelsBySaleIds`는 시간
조건이 없어 `sale_id` 선행이 필요합니다.

**18. 식별자를 타입 래퍼 없이 `String`으로 뒀습니다.** 새 판매 ID는 서버 생성 UUID이며
시드의 `sale-1` 형태는 형식 제약이 아닙니다.

## 운영 관점 (19~20)

**19. `ddl-auto=create-drop`은 기동할 때마다 스키마를 새로 만듭니다.** 인메모리 H2 전용이며
운영 DB에 그대로 쓰면 데이터가 사라집니다.

**20. H2 콘솔이 인증 없이 `/h2-console`에 열려 있습니다.** 채점 편의를 위한 설정입니다.
운영 프로파일에서는 반드시 꺼야 합니다.

## 미구현 범위와 확장 경로

| 항목 | 왜 |
| --- | --- |
| 정산 상태 전이 (대기·확정·지급) | 과제 명시적 제외 |
| CSV 내보내기 | 과제 명시적 제외 |
| 수수료율 이력 테이블 | 인터페이스 뒤에 두는 것까지만 |
| Docker | 과제 명시적 제외 |
| 크리에이터·강의 관리 API | 과제 명시적 제외. 시드로만 존재 |
| 정교한 인증·인가 | 과제가 헤더 방식을 허용 |

**수수료율은 인터페이스까지만 했습니다.** `FeePolicy` + `FixedRateFeePolicy(2000bp)`로 요율을
교체 가능하게 뒀습니다. 요율 값은 도메인이 갖지 않습니다. `application.yml`의
`settlement.fee.basis-points`가 원본이고 `DomainConfig`가 주입합니다. 바꾸려면 설정 한
줄입니다. 시점별 요율(1월은 20%, 2월부터 15%)이 필요해지면 `FeePolicy`에 기간 인자를 넣고
구현체를 하나 더 만듭니다. **계산기는 바뀌지 않습니다.**

**정산 상태 전이를 붙이려면.** `SettlementSummary`는 영속화되지 않는 값 타입이라 매 조회마다
원본 자료에서 다시 계산합니다. 상태 전이를 붙이려면 정산 스냅샷 엔티티를 새로 두고 계산
결과를 그 시점에 고정하면 됩니다. 계산기는 그대로 두고 스냅샷을 만드는 유스케이스와 상태
컬럼을 가진 엔티티가 추가됩니다. **기존 구조를 뜯을 필요가 없습니다.**

**규모가 커지면 세 가지가 순서대로 문제가 됩니다.**

1. **크리에이터 수** — 운영자 집계가 크리에이터마다 포트를 부릅니다. 수백 명이면 배치
   조회로 바꿉니다.
2. **기간 길이** — 순수 계산기가 구간의 판매·취소를 전부 메모리에 올립니다. 상한을 두거나
   집계를 DB로 내립니다.
3. **인덱스** — 두 조회 경로가 상반된 선행 컬럼을 원합니다. 트래픽이 생기면 인덱스를 하나
   더 두거나 커버링 인덱스를 검토합니다.

지금 하지 않은 이유는 "몰라서"가 아니라 "규모가 아니어서"입니다.
