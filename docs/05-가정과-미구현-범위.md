## 원본 과제 이탈 (2~4)

**2. 반열린 구간 채택.** `말일 23:59:59`는 1초 미만 구간을 누락합니다.

**3. 초과 환불 거부 규칙 추가.** 원본에 없습니다. 누적 합계가 원결제액을 넘으면 409입니다.
판정은 `Sale` 애그리게이트가 소유해 `cancel()`을 부르는 어떤 경로도 우회할 수 없습니다. 뺄셈으로 비교합니다. `already + amount`로 쓰면 `@Positive`가 허용하는 `Long.MAX_VALUE`가 오버플로해 음수가 되고 상한 검사를 그냥 통과합니다.

**4. 취소 초기 데이터를 직접 정의.** 금액·귀속월은 과제 서술에서, 시각은 10:00 KST로
고정했습니다.

## 조회 정책 (7)

**7. 빈 월은 404가 아니라 200 + 전 항목 0입니다.** 404로 두면 "정산이 없다"와 "크리에이터가
없다"를 클라이언트가 구분할 수 없습니다. 없는 크리에이터를 조회해도 같습니다.

등록은 다릅니다. `courseExists`로 404를 냅니다. 기준이 다른 것이 아니라 **쓰기와 조회의 위험이 다릅니다.** 없는 강의로 판매를 넣으면 어떤 크리에이터에도 속하지 않는 유령 행이 영구히 남고, 없는 크리에이터를 조회하면 0이 나오고 끝입니다.

## 접근 경계 (8~10)

**8. 액터 헤더는 실제 인증이 아닙니다.** `X-Actor-Role: ADMIN`이라고 쓰면 그냥 운영자가
됩니다. 토큰도 서명도 검증하지 않습니다. 과제가 명시적으로 허용한 단순화입니다. 위조하지 않은 클라이언트까지 통과시킬 이유는 없어 역할 판정은 그대로 겁니다.

**9. 판매·취소 등록을 ADMIN으로 제한했습니다.** 원본에 명시가 없습니다.

**구매 주체와 호출 주체를 나눠서 봤습니다.** 판매를 발생시키는 사람은 수강생입니다.
그래서 누가 샀는지는 요청 본문의 `studentId`에 담깁니다. 반면 이 API를 *호출하는* 쪽은 사람이 아니라 결제 시스템입니다 — 과제가 "실제 결제 시스템 연동 불필요, 데이터 직접 삽입 또는 API로 등록"이라고 적었으므로, 이 엔드포인트는 고객이 누르는 구매 버튼이 아니라 서버 대 서버 연동 창구입니다. ADMIN이 그 대역을 맡습니다.

크리에이터를 배제한 이유는 따로 있습니다. 자기 강의의 판매를 임의로 등록할 수 있으면
**정산을 스스로 부풀릴 수 있습니다.**

실제 서비스라면 결제 게이트웨이용 서비스 계정이나 서명된 웹훅으로 분리할 지점입니다.

**10. 오류 포맷은 RFC 9457이고 초과 환불은 409입니다.** 포맷을 발명하지 않고 Spring 내장
`ProblemDetail`을 씁니다. 409를 고른 것은 요청 형식이 아니라 **자원 상태와의 충돌**이기 때문입니다. 400으로 두면 Bean Validation 실패와 구분되지 않습니다.

## 검증하지 않는 것 (11~14)

**11. 취소 동시성을 보장하지 않습니다.** 같은 판매에 취소 두 건이 동시에 오면 각자 같은
상태를 읽고 각자 합계 검사를 통과할 수 있습니다. **규칙이 도메인에 있다는 것과 원자적으로 적용된다는 것은 다른 문제입니다.**

**실측으로 재현했습니다.** 80,000원 판매(기존 취소 30,000원)에 40,000원 취소를 동시에 두 건
넣으면 둘 다 201이고 누적 110,000원이 됩니다.

막으려면 판매 행을 `SELECT ... FOR UPDATE`로 잠가야 합니다. **`@Version` 낙관적 락은 이 구조에서 듣지 않습니다.** 충돌하는 쓰기가 `sales` UPDATE가 아니라 `cancels` INSERT라 부모 행 버전이 오르지 않고, 어댑터가 로드한 엔티티 대신 같은 값의 새 엔티티를 merge해 dirty check도 UPDATE를 내지 않기 때문입니다.

**12. 미래 시각을 막지 않습니다.** `paidAt`·`cancelledAt`이 현재보다 뒤여도 받습니다. 결제
이전 취소는 409 `CANCEL_BEFORE_PAYMENT`로 거부하지만, 미래 방향에는 기준 시각이 없어 열어 뒀습니다.

**13. ADMIN이 임의의 `paidAt`으로 과거 판매를 등록할 수 있습니다.** 시드 재현에 필요하지만,
이미 마감된 달의 정산을 사후에 바꿀 수 있다는 뜻입니다.

**14. 조회 기간 길이에 상한이 없습니다.** 10년 구간도 받습니다. 운영자 집계는 페이지네이션도
없습니다.

그 밖에 과제 범위라 막지 않은 것들입니다. 로그에 식별자를 그대로 남기므로 개행이 든 `creatorId`로 로그 줄을 위조할 수 있고, 요청 본문 크기 제한과 호출 빈도 제한이 없습니다. 실서비스라면 각각 로그 이스케이프, `server.max-http-request-header-size`, 게이트웨이 레벨 제한으로 다룰 지점입니다.

## 설계 선택 (15~18)

**15. 집계를 DB로 내리지 않고 순수 계산기를 택했습니다.** `SettlementCalculator`는 (기간,
판매, 취소)의 순수 함수라 Spring도 H2도 없이 돕니다. 기간이 길면 해당 구간 자료가 전부 메모리에 올라옵니다. 7건 기준에서 문제없고 설명 가능성을 우선했습니다.

**16. 운영자 집계는 크리에이터 수와 무관하게 조회 3회입니다.** 처음에는 크리에이터마다
포트를 불러 3명에 7회였습니다(1 + 2N). 판매와 취소를 각각 한 번에 읽고 크리에이터별로 묶도록 바꿔 3회가 됐습니다. 조인 결과에 `creatorId`를 실어 오므로 `CancelData`는 그대로 두었습니다 — 계산에 쓰지 않는 필드를 값 객체에 담지 않는다는 규칙을 지켰습니다.

계산 경로는 하나입니다. 단건과 일괄이 같은 `SettlementCalculator`로 끝나고, 두 경로가 같은 값을 내는지 테스트가 잠급니다. 조회 방식이 갈렸다고 계산까지 갈리면 "운영자 집계가 월별 합과 다르다"의 원인이 하나 더 생깁니다.

**17. 두 조회 경로가 상반된 인덱스 선행 컬럼을 원합니다.** `findCancelsBySaleIds`는 시간
조건이 없어 `sale_id` 선행이 필요합니다.

**18. 식별자를 타입 래퍼 없이 `String`으로 뒀습니다.** 새 판매 ID는 서버 생성 UUID이며
시드의 `sale-1` 형태는 형식 제약이 아닙니다.

## 운영 관점 (19~20)

**19. `ddl-auto=create-drop`은 기동할 때마다 스키마를 새로 만듭니다.** 인메모리 H2 전용이며
운영 DB에 그대로 쓰면 데이터가 사라집니다.

**20. H2 콘솔이 인증 없이 `/h2-console`에 열려 있습니다.** 채점 편의를 위한 설정입니다.
운영 프로파일에서는 반드시 꺼야 합니다.

## 미구현 범위와 확장 경로

앞의 넷은 과제가 **선택 구현(추가 점수)** 으로 제시한 항목입니다. 하지 않기로 한 것이지 과제가 제외한 것이 아닙니다. 필수 구현의 정확성을 우선했고, 각각 어디에 어떻게 붙는지는 아래에 적었습니다.

| 항목 | 분류 | 왜 |
| --- | --- | --- |
| 정산 확정 상태 (PENDING → CONFIRMED → PAID) | 선택 구현 | 설계만. 아래 참조 |
| 동일 기간 중복 정산 방지 | 선택 구현 | 확정 상태와 한 몸입니다. 아래 참조 |
| CSV·엑셀 다운로드 | 선택 구현 | 계산 결과를 직렬화하는 층이라 계산기는 바뀌지 않습니다 |
| 수수료율 변경 이력 | 선택 구현 | `FeePolicy` 인터페이스까지. 아래 참조 |
| 크리에이터·강의 관리 API | 요구사항에 없음 | 시드로만 존재합니다 |
| Docker | 요구사항에 없음 | `./gradlew bootRun` 하나로 뜹니다 |
| 정교한 인증·인가 | 과제가 허용 | "인증은 간략 처리 가능 (헤더/파라미터 방식)" |

**수수료율은 인터페이스까지만 했습니다.** `FeePolicy` + `FixedRateFeePolicy(2000bp)`로 요율을
교체 가능하게 뒀습니다. 요율 값은 도메인이 갖지 않습니다. `application.yml`의 `settlement.fee.basis-points`가 원본이고 `DomainConfig`가 주입합니다. 바꾸려면 설정 한 줄입니다. 시점별 요율(1월은 20%, 2월부터 15%)이 필요해지면 `FeePolicy`에 기간 인자를 넣고 구현체를 하나 더 만듭니다. **계산기는 바뀌지 않습니다.**

## 정산 확정 상태를 붙인다면

`PENDING → CONFIRMED → PAID`를 붙일 대상이 지금은 없습니다. 정산은 **매 조회마다 원본에서 다시 계산하는 무상태 값**이고 `SettlementSummary`는 영속화되지 않습니다. 상태는 어떤 레코드의 상태인데 그 레코드가 없습니다.

그래서 순서가 이렇게 됩니다. **먼저 스냅샷을 만들고, 그 위에 상태를 얹습니다.**

```
settlements
  id, creator_id, year_month,
  gross_sales, refunds, net_sales, fee, payout,   ← 확정 시점의 값을 고정
  status,                                          PENDING · CONFIRMED · PAID
  confirmed_at, paid_at
  UNIQUE (creator_id, year_month)
```

```
POST /api/admin/settlements/{creatorId}/{yearMonth}/confirm   계산 → 스냅샷 고정 → CONFIRMED
POST /api/admin/settlements/{creatorId}/{yearMonth}/pay       CONFIRMED → PAID
GET  /api/admin/settlements/{creatorId}/{yearMonth}           스냅샷 조회
```

**동일 기간 중복 정산 방지는 여기서 같이 해결됩니다.** `UNIQUE (creator_id, year_month)`가
같은 달을 두 번 확정하는 것을 DB에서 막습니다. 별도 로직이 필요 없습니다.

**계산기는 바뀌지 않습니다.** 확정 유스케이스가 `SettlementQuery.summarize`를 불러 값을
얻고 스냅샷으로 저장할 뿐입니다. 기존 조회 API도 그대로 실시간 계산을 유지합니다.

### 붙이기 전에 답해야 하는 것

구현하지 않은 진짜 이유는 시간이 아니라 이 셋입니다.

**1. 확정 후 과거 판매가 들어오면 어느 쪽이 맞습니까.** 스냅샷은 그대로고 실시간 계산은
바뀌어 두 값이 갈립니다. 확정의 존재 이유이기도 하지만, 지금 이 시스템의 강점인 "언제 조회해도 같은 값"과 정면으로 부딪힙니다. [가정 13](#운영-관점-1920)의 위험이 실현되는 경로이기도 합니다.

**2. 월별 조회 API는 무엇을 보여줍니까.** 확정 전은 실시간, 확정 후는 스냅샷이면 같은 URL이
시점에 따라 다른 의미를 갖습니다. 늘 실시간이면 확정이 조회에 아무 영향이 없습니다.

**3. 운영자 기간 집계와 단위가 다릅니다.** 확정은 월 단위인데 기간 집계는 임의 구간입니다.
`2025-01-15 ~ 2025-03-20`을 확정할 수는 없습니다.

**셋 다 정책 판단이고 코드보다 먼저 정해야 합니다.** 답 없이 상태 기계만 넣으면 전이는
되는데 그래서 무엇이 달라지는지 설명할 수 없습니다. `PAID`도 실제 송금과 연동돼야 의미가 있는데 이 과제에는 그 연동이 없습니다.

**규모가 커지면 세 가지가 순서대로 문제가 됩니다.**

1. **크리에이터 수** — 조회 횟수는 이미 상수지만, 응답은 전체 크리에이터를 한 번에
돌려줍니다. 수백 명이면 페이지네이션이 필요합니다.
2. **기간 길이** — 순수 계산기가 구간의 판매·취소를 전부 메모리에 올립니다. 상한을 두거나
집계를 DB로 내립니다.
3. **인덱스** — 두 조회 경로가 상반된 선행 컬럼을 원합니다. 트래픽이 생기면 인덱스를 하나
더 두거나 커버링 인덱스를 검토합니다.

지금 하지 않은 이유는 "몰라서"가 아니라 "규모가 아니어서"입니다.
