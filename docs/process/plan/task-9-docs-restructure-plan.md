# Task 9 — 문서 재편: README 허브 + 주제별 한글 문서

## 목표

면접관이 **README 하나로 전체를 탐색**할 수 있게 한다. README는 목차와 실행 정보만 갖고, 내용은 주제별 문서로 나가 링크된다.

## 현재 상태

| 위치 | 파일 | 줄 |
| --- | ---: | ---: |
| `README.md` | 1 | 523 |
| `docs/` | 4 | 785 |
| `docs/plan/` | 7 | 1,151 |
| `docs/spec/` | 45 | 4,559 |
| **합계** | **57** | **7,018** |

문제는 분량이 아니라 **두 종류의 문서가 섞여 있다**는 것이다.

- **읽을 문서** — 면접관이 시스템을 이해하려고 읽는다. 지금은 전부 README 523줄 안에 있다.
- **과정 문서** — 어떻게 만들었는지의 증거다. `plan/` 7개 + `spec/` 45개. 면접관은 이걸 읽지 않는다. 읽으라고 내밀면 오히려 손해다.

README 523줄은 한 화면에 목차가 안 잡힌다. 데이터 모델을 보려면 170행까지 스크롤해야 하고, 그 아래 가정 21항이 또 100줄 이어진다.

## 설계 원칙

**1. 문서 하나가 질문 하나에 답한다.** baeldung 식이다. 제목이 곧 그 문서가 답하는 질문이어야 한다.

**2. README는 목차 + 실행 + 경고.** 80줄 안쪽.

**3. 최우선 경고는 README에 남긴다.** 운영자 기간 집계가 월별 합이 아니라는 것 — 이것만 놓치면 면접관이 API 두 개를 돌려보고 버그로 읽는다. 목차만 남기는 재편에서 **가장 깨지기 쉬운 지점**이다. 링크로 미루지 않고 README 본문에 3줄로 남긴다.

**4. 과정 문서는 읽을 문서와 섞지 않는다.** 번호 붙은 주제 문서만 README가 링크하고, `plan/`·`spec/`은 "구현 과정 기록" 한 줄로 처리한다.

## 결정이 필요한 것

**과정 문서 52개(`plan/` 7 + `spec/` 45)를 어떻게 할 것인가.**

"모두 한글명으로"를 문자 그대로 적용하면 52개 파일명을 바꾸고 **`docs/spec/` 안의 상대 링크 76개**를 같이 고쳐야 한다. 얻는 것과 비용을 따져야 한다.

| 안 | 내용 | 비용 | 얻는 것 |
| --- | --- | --- | --- |
| A | 현행 유지, README에서 한 줄 링크 | 0 | 과정 문서가 `task-N` 순서로 읽힌다 |
| B | `docs/process/` 아래로 이동 | 링크 76개 | 읽을 문서와 과정 문서가 디렉터리로 갈린다 |
| C | 전부 한글 파일명 | 링크 76개 + 파일명 52개 | 이름이 통일된다 |

C를 권하지 않는다. 면접관은 이 52개를 읽지 않는다. `task-4-3-register-cancel-spec.md`가 `태스크-4-3-취소-등록-명세.md`가 되어도 그 사실은 안 바뀌고, `task-N` 접두사가 사라지면 빌드 순서로 읽던 단서를 잃는다.
