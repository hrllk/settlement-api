# 영속성 설계 결정

Task 7 README의 원본이자 설계 근거 정리다. 각 항목은 **무엇을 했나 / 왜 / 안 쓴 대안**으로 적는다.

## 요약

JPA를 **타입 있는 쿼리 실행기**로만 쓴다. 연관 매핑, 지연 로딩, 더티 체킹, 캐스케이드를 쓰지 않는다. 쿼리는 JPQL로 명시하고 조인 경로는 서브쿼리로 드러낸다.

실제 사용 표면:

| 기능 | 사용 |
| --- | ---: |
| `@ManyToOne` / `@OneToMany` / `FetchType` / `Cascade` | 0 |
| `@Transactional` / `EntityManager` | 0 |
| `.save()` / `.flush()` / `.merge()` | 0 (Task 4에서 저장 경로만 추가) |

## 1. JPA를 택했다

Spring Data JPA의 파생 쿼리와 `@Query`로 조회 4종을 덮는다. 엔티티가 타입 있는 스키마 문서 역할을 하고, `ddl-auto`가 스키마를 만들어 준다.

**MyBatis를 안 쓴 이유.** 이 프로젝트는 조회 4개, 저장 2개가 전부다. XML이나 애노테이션 SQL을 따로 관리할 만큼 쿼리가 복잡하지 않고, `schema.sql`을 손으로 써야 한다. 헥사고날 구조라 갈아끼우는 범위가 `adapter/out/persistence`로 한정되므로 필요해지면 그때 바꿔도 비용이 같다.

**`JdbcTemplate`을 안 쓴 이유.** 결과 매핑을 전부 손으로 써야 하는데 얻는 게 없다.

## 2. 연관 매핑을 걸지 않았다

`SaleEntity.courseId`, `CancelEntity.saleId`는 평범한 문자열 컬럼이다.

**이유.** `@ManyToOne`을 걸면 지연 로딩 프록시가 생기고 N+1이 따라온다. 더 나쁜 것은 **어댑터가 어떤 쿼리를 던지는지 코드만 봐서는 알 수 없게 된다**는 점이다. 필요한 조인은 리포지토리가 JPQL 서브쿼리로 명시한다.

```java
where s.courseId in (select c.id from CourseEntity c where c.creatorId = :creatorId)
```

어떤 테이블을 거치는지 그대로 보인다.

**결과.** 이 프로젝트에는 N+1이 발생할 지점이 없다. 판매 목록의 환불 상태도 `findBySaleIdIn`으로 한 번에 가져와 2쿼리로 끝난다.

## 3. FK 제약을 걸지 않았다

`ddl-auto`가 만드는 스키마에 연관 매핑이 없으므로 FK도 없다.

**대신 애플리케이션이 막는다.** 없는 `courseId`로 판매를 등록하는 요청은 Task 4가 `courseExists`로 걸러 `CourseNotFoundException` 404를 준다.

**FK에 맡기지 않은 이유.** `DataIntegrityViolationException`이 올라오면 그건 500이다. 사용자 입력 오류를 서버 오류로 보고하게 된다. 검증은 요청을 받는 쪽에서 해야 응답 코드가 의미를 갖는다.

## 4. setter를 만들지 않았다

엔티티 넷 모두 getter만 있다. Lombok도 `@Setter`를 붙이지 않는다.

**이유.** 판매 금액이나 결제 시각이 사후에 바뀌면 **이미 조회된 정산이 조용히 달라진다.** 3월 정산으로 120,000원을 받았는데 나중에 같은 달이 다른 값이 되는 것은 정산 API에서 버그다.

**따라서 더티 체킹을 쓰지 않는다.** 변경 감지로 UPDATE가 나가는 경로가 아예 없다. 취소 추가는 새 행 INSERT다.

## 5. 시간은 `Instant`다

`LocalDateTime`을 쓰지 않는다.

**이유.** `LocalDateTime`은 오프셋을 잃는다. `sale-5`의 결제 시각은 `2025-01-31T23:30+09:00`이고 UTC로는 `2025-01-31T14:30Z`다. 오프셋이 없으면 이 값이 KST 1월인지 2월인지 **값만 보고 판단할 수 없다.** KST 1월 구간은 `[2024-12-31T15:00Z, 2025-01-31T15:00Z)`이고 이 값은 그 안에 30분 남기고 들어간다.

시간대 변환 책임은 `SettlementPeriod` 하나에 격리했다. 어댑터와 리포지토리는 시간대를 모르고 `Instant`만 주고받는다.

## 6. 반열린 구간을 쿼리에 직접 쓴다

```sql
paid_at >= :fromInclusive and paid_at < :toExclusive
```

**`between`을 쓰지 않는다.** 양끝이 닫혀 종료 경계가 포함된다. 원본 과제는 월 경계를 "말일 23:59:59"로 적었는데 그러면 초 미만 구간이 누락된다. 반열린 구간으로 의도적으로 이탈했고 도메인이 그 판단을 경계 테스트 3방향으로 잠갔다. 어댑터에서 `between`을 쓰면 그 판단이 여기서 무너진다.

## 7. 인덱스 컬럼 순서를 뒤집지 않았다

| 조회 | 원하는 선행 컬럼 |
| --- | --- |
| 크리에이터별 판매 | `course_id` |
| 기간별 전체 판매 | `paid_at` |
| `findCancelsBySaleIds` | `sale_id` (**시간 조건이 아예 없음**) |

**두 조회 경로가 상반된 순서를 원한다.** `(cancelled_at, sale_id)`로 두면 시간 조건 없는 조회가 선행 컬럼을 못 써 풀스캔이 된다. 데이터가 7건이라 실측 차이가 0이므로 인덱스를 늘리지 않고 현행을 유지했다. 실제 트래픽에서는 인덱스를 하나 더 두거나 커버링 인덱스를 검토할 지점이다.

## 8. 읽기 모델과 쓰기 모델을 나눴다

| 방향 | 인터페이스 | 위치 | 돌려주는 것 |
| --- | --- | --- | --- |
| 읽기 | `SalesQueryPort` | `application/port/out` | `SaleData` / `CancelData` / `SaleRecord` 값 |
| 쓰기 | `SaleRepository` | `domain/sales` | `Sale` 애그리게이트 |

**읽기가 애그리게이트를 안 쓰는 이유는 N+1이다.** 판매 목록 응답을 만들려고 애그리게이트를 N개 로딩하면 각각이 자기 취소를 딸고 온다. 목록은 2쿼리로 끝나야 한다.

**쓰기가 애그리게이트를 쓰는 이유는 불변식이다.** 누적 환불 ≤ 원결제는 판매와 그 취소들이 함께 지켜야 하는 규칙이다. `sale.cancel(...)` 안에 두면 그 메서드를 부르는 모든 경로가 규칙을 통과한다. 유스케이스에 두면 다른 경로가 생겼을 때 비교문을 빠뜨려도 컴파일이 통과한다.

**두 방향의 필요가 달라서 모델이 갈리는 것**이지 패턴을 적용한 게 아니다.

## 9. `ddl-auto=create-drop` + `data.sql`

메모리 H2라 매 기동마다 스키마를 새로 만든다. 스키마 파일을 유지보수하지 않고 엔티티가 단일 진실이 된다.

`spring.jpa.defer-datasource-initialization=true`가 `data.sql`을 Hibernate DDL **이후**에 실행시킨다. 이게 없으면 테이블 없는 상태로 INSERT가 나가 기동이 통째로 실패한다.

**운영 환경이라면 안 쓴다.** Flyway나 Liquibase로 마이그레이션을 버전 관리해야 한다. 과제 범위에서 제외했다.

## 10. Lombok은 영속성 계층에만

엔티티는 `@Getter` + `@NoArgsConstructor(PROTECTED)`, 어댑터는 `@RequiredArgsConstructor`다.

| 안 쓴 것 | 이유 |
| --- | --- |
| `@Data`, `@EqualsAndHashCode` | equals/hashCode가 전체 필드 기반이 되어 JPA 식별자 의미론과 어긋나고 프록시에서 깨진다 |
| `@ToString` | 연관을 걸면 지연 로딩을 건드린다 |
| `@Setter` | 4번 참조 |
| `@AllArgsConstructor` | 시그니처가 필드 선언 순서에 묶인다. `SaleEntity(String id, String courseId, ...)`는 `String`이 인접해 순서를 바꿔도 호출부가 컴파일된다 |

`domain`에는 쓰지 않는다. 전부 `record`라 Lombok이 할 일이 없다.

## 예상 질문과 답

**N+1은 어떻게 막았나요**
연관 매핑을 걸지 않았습니다. 조인이 필요한 곳은 JPQL 서브쿼리로 명시했고, 판매 목록의 환불 상태는 `findBySaleIdIn`으로 한 번에 가져와 2쿼리로 끝냅니다.

**영속성 컨텍스트 관리는 어떻게 하나요**
조회 어댑터는 읽기 전용이라 관리할 상태가 없습니다. 쓰기는 애그리게이트를 적재해 새 취소만 INSERT하고, 더티 체킹에 기대지 않습니다.

**왜 `@Transactional`이 없나요**
Task 2까지는 조회뿐입니다. 쓰기가 생기는 Task 4의 유스케이스에 붙습니다.

**엔티티를 도메인 모델로 쓰지 않은 이유는**
정산 계산은 평평한 값의 합산이고 등록은 불변식이 필요합니다. 필요가 다르면 모델도 다릅니다. 그리고 영속성 애노테이션이 도메인에 들어오면 도메인 테스트가 Spring 없이 못 돕니다. 실제로 계산기 테스트 42건이 컨텍스트 없이 돌아갑니다.

**MyBatis가 더 낫지 않나요**
쿼리가 조회 4개, 저장 2개뿐이라 SQL을 따로 관리할 이득이 작았습니다. 헥사고날이라 갈아끼우는 범위가 어댑터 9개 파일로 한정되므로 필요해지면 도메인을 안 건드리고 바꿀 수 있습니다.

**동시성은 어떻게 처리했나요**
처리하지 않았습니다. 취소 요청 둘이 동시에 오면 각자 상태를 읽고 각자 검사를 통과할 수 있습니다. 막으려면 판매 행 잠금(`SELECT ... FOR UPDATE`)이 필요합니다. `@Version` 낙관적 락은 여기서 듣지 않습니다 — 충돌하는 쓰기가 `sales` UPDATE가 아니라 `cancels` INSERT라 부모 행 버전이 오르지 않고, 어댑터가 로드한 엔티티 대신 같은 값의 새 엔티티를 merge해 dirty check도 UPDATE를 내지 않기 때문입니다. 과제 범위에서 뺐고 README에 가정으로 남겼습니다. 애그리게이트가 규칙을 소유한다는 것과 그 규칙이 원자적으로 적용된다는 것은 다른 문제입니다.

## 하지 않은 것

- 마이그레이션 도구(Flyway/Liquibase)
- 낙관적/비관적 락
- 2차 캐시
- 페이징 — 판매 목록이 7건이라 필요가 없다
- 감사 필드(`createdAt`/`updatedAt`) — 정산 계산에 안 쓰인다
