## 무엇을 정산하는가


```text
  수강생 ──── 결제 ────▶ 강의 ────▶ 크리에이터
                          │
                          │  플랫폼이 순 판매액의 20%를 수수료로 뗍니다
                          ▼
                     정산 예정 금액  (크리에이터가 받을 돈)

  수강생 ──── 취소 ────▶ 환불이 발생하면 그만큼 순 판매액에서 빠집니다
```

| 등장인물 | 하는 일 | 이 API에서 |
| --- | --- | --- |
| 수강생 | 강의를 삽니다. 취소하기도 합니다 | 판매 기록의 `studentId`로만 남습니다 |
| 크리에이터 | 강의를 만들어 팝니다 | 자기 정산을 조회합니다 |
| 플랫폼 | 판매를 중개하고 수수료를 뗍니다 | 수수료율 20%를 소유합니다 |
| 운영자 | 플랫폼을 운영합니다 | 전체 크리에이터 정산을 집계합니다 |

**정산은 "이번 달에 이 크리에이터에게 얼마를 줄지" 계산하는 일입니다.** 판 금액을 모두
더하고, 환불된 만큼 빼고, 남은 금액에서 수수료를 뗍니다. 그 결과가 정산 예정 금액입니다.

어려운 지점은 둘입니다. **환불이 다른 달에 일어나면 어느 달에 넣느냐**(→ [이중 집계 처리방식](#이중-집계-처리방식)),
그리고 **여러 달을 한 번에 조회하면 월별 합과 달라진다**(→ [운영자 기간집계](#운영자-기간집계--월별-정산-합))는 것입니다.

## 계산식

```text
netSales = grossSales - refunds
fee      = netSales <= 0 ? 0 : netSales * 2000 / 10000   // 20%, 버림
payout   = netSales - fee
```

응답에 담기는 일곱 값입니다. 오른쪽 열은 시드로 실제 조회한 creator-1의 2025-03입니다.

| 필드 | 한글 | 어떻게 나오나 | creator-1 2025-03 |
| --- | --- | --- | ---: |
| `grossSales` | 총 판매 금액 | 기간 내 `paidAt` 판매의 합 | 260,000 |
| `saleCount` | 판매 건수 | 기간 내 `paidAt` 판매의 수 | 4 |
| `refunds` | 환불 금액 | 기간 내 `cancelledAt` 취소의 합 | 110,000 |
| `cancelCount` | 취소 건수 | 기간 내 `cancelledAt` 취소의 수 | 2 |
| `netSales` | 순 판매 금액 | `grossSales − refunds` | 150,000 |
| `fee` | 플랫폼 수수료 | 순 판매의 20%, 버림. 순 판매가 0 이하면 0 | 30,000 |
| `payout` | 정산 예정 금액 | `netSales − fee` | 120,000 |

`grossSales`와 `refunds`는 **기준 컬럼이 다릅니다.** 판매는 `paidAt`, 환불은 `cancelledAt`으로 각각 귀속 월을 정합니다 — [(이중 집계 처리방식)](#이중-집계-처리방식)

`netSales`·`fee`·`payout`은 파생값이지만 응답에 전부 담습니다. 클라이언트가 다시 계산하면 서버와 갈립니다. 특히 `fee`는 순 판매가 음수일 때 0으로 막히므로 20%를 곱해서는 나오지 않습니다.

음수 판정이 나눗셈보다 **먼저**인 것이 정책입니다. `long` 나눗셈은 0 방향 절단이라 순서가 바뀌면 −60,000에서 −12,000이 나와 플랫폼이 크리에이터에게 수수료를 돌려주는 셈이 됩니다.

## 운영자 기간집계 != 월별 정산 합

**같은 크리에이터를 1~3월로 조회하면 48,000원인데, 1월·2월·3월을 따로 조회해 더하면
36,000원입니다.** 버그가 아닙니다. 왜 이런 일이 생기는지부터 봅니다.

### creator-2에게 일어난 일

```text
1월   60,000원짜리 강의가 팔렸다
2월   그 강의가 취소돼 60,000원을 환불했다
3월   다시 60,000원짜리가 팔렸다
```

판 것도 60,000, 되돌린 것도 60,000입니다. 결국 남은 건 3월의 60,000원 하나뿐입니다.

### 문제는 수수료가 한 방향으로만 움직인다는 것

플랫폼 수수료는 **매출에서 떼는** 값입니다. 그래서 매출이 마이너스인 달에는 뗄 게 없어 0원입니다. **이미 뗀 수수료를 돌려주지는 않습니다.**

달을 따로따로 보면 이렇게 됩니다.

```text
월별로 끊어 보면
  1월   60,000 팔았다   → 수수료 12,000 떼고    48,000 받음
  2월   60,000 물어줬다 → 뗄 매출이 없어 수수료 0,  −60,000
  3월   60,000 팔았다   → 수수료 12,000 떼고    48,000 받음
                                            합계  36,000
```

2월에 60,000원을 통째로 물어냈는데, **1월에 이미 떼인 12,000원은 돌아오지 않습니다.** 그래서 1월과 2월이 서로 상쇄되지 못하고 12,000원만큼 손해가 남습니다.

기간 전체를 한 바구니로 보면 상쇄가 먼저 일어납니다.

```text
1~3월을 한 번에 보면
  판 것   60,000 + 60,000 = 120,000
  물어준 것              −  60,000
  남은 매출                 60,000  → 수수료 12,000 → 48,000
```

1월 매출과 2월 환불이 먼저 지워지고, **살아남은 60,000원에만 수수료가 붙습니다.** 그래서 48,000원입니다. 차이 12,000원이 바로 "돌려받지 못한 1월 수수료"입니다.

### 세 명을 모두 더하면

운영자 집계는 크리에이터별 정산을 그대로 더한 값입니다. 1~3월을 한 번에 조회하면 이렇게 나옵니다.

| 크리에이터 | 1월 | 2월 | 3월 | 월별 합 | 단일 구간 | 차이 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| creator-1 | 0 | 0 | 120,000 | 120,000 | 120,000 | 0 |
| creator-2 | 48,000 | −60,000 | 48,000 | 36,000 | 48,000 | **−12,000** |
| creator-3 | 0 | 96,000 | 0 | 96,000 | 96,000 | 0 |
| | | | | **252,000** | **264,000** | **−12,000** |

같은 세 명을 달마다 따로 계산해 더하면 252,000원입니다.

**차이 12,000원은 전부 creator-2 한 명에게서 나옵니다.** 나머지 둘은 어떻게 계산하든 같습니다 — creator-1은 판매와 환불이 모두 3월 안에 있고, creator-3은 환불이 없습니다.

**판매와 환불이 다른 달에 걸친 크리에이터에게만 차이가 생깁니다.**

### 단일 구간을 고른 이유

월별로 끊으면 **마이너스인 달마다 이 손해가 반복됩니다.** 크리에이터에게 불리하고, "왜 월별 합과 다르냐"는 질문에 답할 방법도 없습니다.

한 바구니로 보면 답이 하나입니다. 판 것에서 물어준 것을 빼고, 남은 만큼만 수수료를 뗍니다.

월별 조회와 운영자 집계는 `SettlementQuery` **한 곳**을 씁니다. 두 경로의 차이가 기간 하나뿐이라는 것을 코드 구조로 못 박았습니다.

## 수수료는 0에서 멈추고, 정산 예정액은 마이너스로 갑니다

둘 다 금액인데 **한쪽만 마이너스를 허용합니다.** 헷갈리기 쉬운 지점이라 따로 적습니다.

| | 무엇인가 | 마이너스가 되나 |
| --- | --- | --- |
| 수수료 | 플랫폼이 매출에서 떼어 가는 몫 | 안 됩니다. 최소 0 |
| 정산 예정액 | 실제로 주고받을 돈 | 됩니다 |

**수수료가 마이너스가 되면 플랫폼이 크리에이터에게 돈을 주는 뜻이 됩니다.** 뗄 매출이
없을 뿐이지 거꾸로 줘야 할 이유는 없으므로 0에서 멈춥니다.

**정산 예정액은 반대입니다.** 마이너스는 "크리에이터가 플랫폼에 돌려줄 돈"이라는 뜻을
갖습니다. creator-2의 2025-02가 −60,000원인데, 판매 없이 환불만 있었으니 맞는 값입니다. 응답에서 0으로 깎거나 절댓값을 씌우면 이 정보가 사라집니다.


## 반열린 구간

```text
2025-03 → [2025-03-01 00:00 KST, 2025-04-01 00:00 KST)
        = [2025-02-28 15:00 Z,   2025-03-31 15:00 Z)
```

시작은 포함, 끝은 배제입니다.

**원본 과제의 `말일 23:59:59`를 의도적으로 이탈했습니다.** 그 표현은 `23:59:59.001`부터
`23:59:59.999`까지 1초 미만 구간을 통째로 누락합니다. 밀리초 정밀도로 저장하는 시스템에서 그 사이에 결제가 들어오면 **어느 달에도 잡히지 않습니다.**

반열린 구간은 인접한 달이 빈틈도 겹침도 없이 이어집니다. 2월의 끝과 3월의 시작이 같은 순간이고, 그 순간은 3월에만 속합니다.

`from`/`to`는 사용자 표기(양끝 포함)로 받아서 반열린 구간으로 바꿉니다.

```text
?from=2025-03-01&to=2025-03-31
  → [2025-03-01 00:00 KST, 2025-04-01 00:00 KST)
                            ^ 종료일 + 1일
```

응답의 `to`는 요청 문자열을 그대로 되돌려준 것이지 내부의 `toExclusive`가 아닙니다.

## KST 처리 방식

시드에서 KST와 UTC의 날짜가 갈리는 레코드는 `sale-5` 하나뿐입니다.

```text
          KST 2025-01                    │          KST 2025-02
├─────────────────────────────────────────)├────────────────────────────
2024-12-31T15:00Z            2025-01-31T15:00Z            2025-02-28T15:00Z
                                    ▲
                    sale-5   2025-01-31T14:30Z  (KST 01-31 23:30)
                    경계 30분 전  →  1월 귀속
                                                  ▲
                                cancel-3   2025-02-03T01:00Z  (KST 02-03 10:00)
                                                  →  2월 귀속
```

**같은 거래인데 판매는 1월, 환불은 2월입니다.** `)` 기호가 상한 배제입니다.

### 저장은 Instant, 해석은 KST

DB에는 UTC 순간을 저장합니다. KST 연월·일자를 `Instant` 구간으로 바꾸는 책임은 `SettlementPeriod` **한 클래스에만** 있습니다. 계산기와 어댑터는 시간대를 모릅니다.

## 이중 집계 처리방식

**판매는 `paidAt`, 환불은 `cancelledAt`으로 각각 귀속 기간을 판단합니다.**

| | 기준 컬럼 |
| --- | --- |
| 총 판매액, 판매 건수 | `paidAt` |
| 환불액, 취소 건수 | `cancelledAt` |

**금액뿐 아니라 건수도 같은 기준을 따릅니다.** creator-2의 2025-02는 판매 건수 0, 취소 건수 1입니다. 판매가 없는데 취소만 있는 달이 실재합니다. 그래서 응답에 판매 건수와 취소 건수를 따로 담습니다. 하나로 합치면 이 달이 "1건"으로 보여 판매가 있었는지 알 수 없습니다.

### 환불 상태만 기간과 무관

집계 금액은 기간으로 나뉘지만 **판매별 환불 상태는 나뉘지 않습니다.** 그 판매에 연결된 **모든** 취소를 봅니다.

`sale-5`를 1월 판매 목록으로 조회하면 환불 상태가 `FULL`입니다. 취소는 2월이지만 상태는 **판매의 속성**이지 기간의 속성이 아닙니다. 
1월 창으로 취소를 조회하면 `cancel-3`이 잡히지않아 `NONE`이 나오는데, 그건 틀린 답입니다.

**금액은 기간으로 자르고, 상태는 자르지 않습니다.** 이 구분이 이 프로젝트에서 가장 헷갈리는 지점입니다.
