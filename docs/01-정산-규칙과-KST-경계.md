## 계산식

```text
netSales = grossSales - refunds
fee      = netSales <= 0 ? 0 : netSales * 2000 / 10000   // 20%, 버림
payout   = netSales - fee
```

응답에 담기는 일곱 값입니다. 오른쪽 열은 시드로 실제 조회한 creator-1의 2025-03입니다.

| 필드 | 한글 | 어떻게 나오나 | creator-1 2025-03 |
| --- | --- | --- | ---: |
| `grossSales` | 총 판매 금액 | 기간 내 `paidAt` 판매의 합 | 260,000 |
| `saleCount` | 판매 건수 | 기간 내 `paidAt` 판매의 수 | 4 |
| `refunds` | 환불 금액 | 기간 내 `cancelledAt` 취소의 합 | 110,000 |
| `cancelCount` | 취소 건수 | 기간 내 `cancelledAt` 취소의 수 | 2 |
| `netSales` | 순 판매 금액 | `grossSales − refunds` | 150,000 |
| `fee` | 플랫폼 수수료 | 순 판매의 20%, 버림. 순 판매가 0 이하면 0 | 30,000 |
| `payout` | 정산 예정 금액 | `netSales − fee` | 120,000 |

`grossSales`와 `refunds`는 **기준 컬럼이 다릅니다.** 판매는 `paidAt`, 환불은 `cancelledAt`으로
각각 귀속 월을 정합니다 — [이중 집계 기준](#이중-집계-기준)을 보십시오.

`netSales`·`fee`·`payout`은 파생값이지만 응답에 전부 담습니다. 클라이언트가 다시 계산하면
서버와 갈립니다. 특히 `fee`는 순 판매가 음수일 때 0으로 막히므로 20%를 곱해서는 나오지 않습니다.

음수 판정이 나눗셈보다 **먼저**인 것이 정책입니다. `long` 나눗셈은 0 방향 절단이라 순서가
바뀌면 −60,000에서 −12,000이 나와 플랫폼이 크리에이터에게 수수료를 돌려주는 셈이 됩니다.

## 운영자 기간 집계는 월별 정산의 합이 아닙니다

기간 전체를 **하나의 정산 구간**으로 계산합니다. 월별로 계산해 더하지 않습니다.

```text
단일 구간 (채택):  (60,000 + 60,000) − 60,000 = 60,000  → 수수료 12,000 → 48,000

월별 합산:   1월  60,000 − 0      =  60,000 → 수수료 12,000 →  48,000
             2월       0 − 60,000 = −60,000 → 수수료      0 → −60,000
             3월  60,000 − 0      =  60,000 → 수수료 12,000 →  48,000
                                                        합계     36,000
```

12,000원 차이는 월별 합산일 때 2월의 음수 순 판매액에 **수수료 0원 제한**이 걸려 1월에 이미
뗀 수수료가 상쇄되지 않기 때문입니다. 기간 전체로 보면 1월 매출과 2월 환불이 먼저 상쇄되고
남은 60,000원에만 수수료가 붙습니다. 전체 합계로는 단일 구간 **264,000원**, 월별 합산
252,000원입니다.

월별 합산을 쓰지 않는 이유는 두 가지입니다. 음수 월마다 제한이 반복 적용되어 크리에이터에게
불리하고, "왜 월별 합과 다른가"를 설명할 수 없습니다.

월별 조회와 운영자 집계는 `SettlementQuery` **한 곳**을 씁니다. 두 경로의 차이가 기간
하나뿐이라는 것을 구조로 보장합니다.

## 수수료와 정산 예정액은 다른 종류의 수입니다

수수료는 플랫폼이 **매출에 부과하는** 값이라 매출이 음수면 부과할 대상이 없습니다. 정산
예정액은 실제 **채권·채무**라 음수가 "크리에이터가 돌려줄 금액"이라는 의미를 갖습니다.
응답에서 0으로 깎거나 절댓값을 취하지 않습니다.

금액은 원 단위 `long`이고 수수료는 버림입니다. 양수 구간에서 `long` 나눗셈의 절단이 곧
버림입니다. 순 판매액 33,333원이면 수수료는 6,666원입니다(실제 6,666.6).

## 반열린 구간

```text
2025-03 → [2025-03-01 00:00 KST, 2025-04-01 00:00 KST)
        = [2025-02-28 15:00 Z,   2025-03-31 15:00 Z)
```

시작은 포함, 끝은 배제입니다.

**원본 과제의 `말일 23:59:59`를 의도적으로 이탈했습니다.** 그 표현은 `23:59:59.001`부터
`23:59:59.999`까지 1초 미만 구간을 통째로 누락합니다. 밀리초 정밀도로 저장하는 시스템에서
그 사이에 결제가 들어오면 **어느 달에도 잡히지 않습니다.**

반열린 구간은 인접한 달이 빈틈도 겹침도 없이 이어집니다. 2월의 끝과 3월의 시작이 같은
순간이고, 그 순간은 3월에만 속합니다.

`from`/`to`는 사용자 표기(양끝 포함)로 받아서 반열린 구간으로 바꿉니다.

```text
?from=2025-03-01&to=2025-03-31
  → [2025-03-01 00:00 KST, 2025-04-01 00:00 KST)
                            ^ 종료일 + 1일
```

응답의 `to`는 요청 문자열을 그대로 되돌려준 것이지 내부의 `toExclusive`가 아닙니다.

## 월 경계 타임라인

시드에서 KST와 UTC의 날짜가 갈리는 레코드는 `sale-5` 하나뿐입니다.

```text
          KST 2025-01                    │          KST 2025-02
├─────────────────────────────────────────)├────────────────────────────
2024-12-31T15:00Z            2025-01-31T15:00Z            2025-02-28T15:00Z
                                    ▲
                    sale-5   2025-01-31T14:30Z  (KST 01-31 23:30)
                    경계 30분 전  →  1월 귀속
                                                  ▲
                                cancel-3   2025-02-03T01:00Z  (KST 02-03 10:00)
                                                  →  2월 귀속
```

**같은 거래인데 판매는 1월, 환불은 2월입니다.** `)` 기호가 상한 배제입니다.

## 저장은 Instant, 해석은 KST

DB에는 UTC 순간을 저장합니다. KST 연월·일자를 `Instant` 구간으로 바꾸는 책임은
`SettlementPeriod` **한 클래스에만** 있습니다. 계산기와 어댑터는 시간대를 모릅니다.

**`LocalDateTime`을 쓰지 않았습니다.** 값이 KST인지 UTC인지 코드에 남지 않아, `sale-5`가
1월 대신 2월로 귀속되는 사고의 전형적 원인입니다.

## 이중 집계 기준

**판매는 `paidAt`, 환불은 `cancelledAt`으로 각각 귀속 기간을 판단합니다.**

| | 기준 컬럼 |
| --- | --- |
| 총 판매액, 판매 건수 | `paidAt` |
| 환불액, 취소 건수 | `cancelledAt` |

**금액뿐 아니라 건수도 같은 기준을 따릅니다.** creator-2의 2025-02는 판매 건수 0, 취소 건수
1입니다. 판매가 없는데 취소만 있는 달이 실재합니다. 그래서 응답에 판매 건수와 취소 건수를
따로 담습니다. 하나로 합치면 이 달이 "1건"으로 보여 판매가 있었는지 알 수 없습니다.

## 환불 상태만 기간과 무관합니다

집계 금액은 기간으로 나뉘지만 **판매별 환불 상태는 나뉘지 않습니다.** 그 판매에 연결된
**모든** 취소를 봅니다.

`sale-5`를 1월 판매 목록으로 조회하면 환불 상태가 `FULL`입니다. 취소는 2월이지만 상태는
**판매의 속성**이지 기간의 속성이 아닙니다. 1월 창으로 취소를 조회하면 `cancel-3`이 잡히지
않아 `NONE`이 나오는데, 그건 틀린 답입니다.

**금액은 기간으로 자르고, 상태는 자르지 않습니다.** 이 구분이 이 프로젝트에서 가장 헷갈리는
지점입니다.
