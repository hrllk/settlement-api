# Task 2.6 — `data.sql` 초기 데이터 17행 명세

부모: [`task-2-sales-seed-data-spec.md`](./task-2-sales-seed-data-spec.md) · 의존 2.1, 2.2 · 10분

## 실행 순서

Task 1이 `spring.jpa.defer-datasource-initialization=true`를 넣었다. 이게 없으면 `data.sql`이 Hibernate DDL보다 먼저 돌아 테이블 없는 상태로 INSERT가 나가고 기동이 통째로 실패한다. **이 설정이 지워지면 Task 2가 전부 깨진다.**

`spring.sql.init.mode`는 내장 DB에서 기본이 `embedded`라 별도 설정이 필요 없다.

## 내용

```sql
-- creators
insert into creators (id, name) values
  ('creator-1', '김강사'), ('creator-2', '이강사'), ('creator-3', '박강사');

-- courses
insert into courses (id, creator_id, title) values
  ('course-1', 'creator-1', 'Spring Boot 입문'), ('course-2', 'creator-1', 'JPA 실전'),
  ('course-3', 'creator-2', 'Kotlin 기초'), ('course-4', 'creator-3', 'MSA 설계');

-- sales  (주석은 KST, 값은 UTC)
insert into sales (id, course_id, amount, paid_at) values
  ('sale-1', 'course-1',  50000, '2025-03-05T01:00:00Z'),  -- 2025-03-05 10:00 KST
  ('sale-2', 'course-1',  50000, '2025-03-15T05:30:00Z'),  -- 2025-03-15 14:30 KST
  ('sale-3', 'course-2',  80000, '2025-03-20T00:00:00Z'),  -- 2025-03-20 09:00 KST
  ('sale-4', 'course-2',  80000, '2025-03-22T02:00:00Z'),  -- 2025-03-22 11:00 KST
  ('sale-5', 'course-3',  60000, '2025-01-31T14:30:00Z'),  -- 2025-01-31 23:30 KST  ← 월 경계
  ('sale-6', 'course-3',  60000, '2025-03-10T07:00:00Z'),  -- 2025-03-10 16:00 KST
  ('sale-7', 'course-4', 120000, '2025-02-14T01:00:00Z');  -- 2025-02-14 10:00 KST

-- cancels
insert into cancels (id, sale_id, amount, cancelled_at) values
  ('cancel-1', 'sale-3', 80000, '2025-03-25T01:00:00Z'),   -- 2025-03-25 10:00 KST  전액
  ('cancel-2', 'sale-4', 30000, '2025-03-26T01:00:00Z'),   -- 2025-03-26 10:00 KST  부분
  ('cancel-3', 'sale-5', 60000, '2025-02-03T01:00:00Z');   -- 2025-02-03 10:00 KST  전액, 월 경계
```

이름과 제목은 원본 과제 JSON의 값을 그대로 쓴다. 자리표시자를 쓰면 평가자가 자기 데이터와 대조할 때 한 번 더 매핑해야 한다.

## KST 주석이 필수인 이유

`sale-5`의 저장값은 `2025-01-31T14:30:00Z`다. UTC 값만 보면 1월 31일이 맞으니 이상해 보이지 않는다. 그런데 이 판매가 **KST 기준 1월에 귀속되는지 2월인지**는 UTC 값만으로 판단할 수 없다. KST 1월의 구간은 `[2024-12-31T15:00Z, 2025-01-31T15:00Z)`이고 `14:30Z`는 그 안에 30분 남기고 들어간다. 주석이 없으면 이 30분이 왜 중요한지 아무도 모른다.

리뷰어가 시드를 읽고 "이 값이 맞나"를 판단할 수 있어야 한다. 주석이 그 판단의 유일한 근거다.

## 취소 시각을 Task 2가 정한다

Task 3 기준표는 취소의 **날짜만** 확정했다. 시각은 정하지 않았다. 세 건 모두 **10:00 KST**로 고정한다. 자정과 자정 직전에서 멀어 어떤 구간 구현에서도 귀속 월이 흔들리지 않는다. 경계 근처로 잡으면 시드가 경계 테스트를 겸하게 되는데, 경계 검증은 Task 3의 픽스처가 이미 세 방향으로 잠갔다. 시드는 시나리오 재현만 한다. 이 선택을 README에 남긴다.

## 17행이 전부다

Task 3의 추가 테스트 케이스(순 판매액 33,333원 수수료 버림, 동일 판매 다수 부분 취소 등)를 **시드에 넣으면 안 된다.** 넣는 순간 creator-1의 2025-03 기대값 120,000원이 깨진다. 그 값은 원본 과제가 명시한 숫자라 바꿀 수 없다. 추가 케이스는 Task 3의 단위 테스트 픽스처로만 존재한다.

## 검산 결과

이 17행으로 계산한 값이 Task 3 기준표와 전부 일치한다.

| 크리에이터 | 월 | 총 판매(건) | 환불(건) | 순 판매 | 수수료 | 정산 예정 |
| --- | --- | --- | --- | --- | --- | --- |
| creator-1 | 2025-03 | 260,000 (4) | 110,000 (2) | 150,000 | 30,000 | 120,000 |
| creator-2 | 2025-01 | 60,000 (1) | 0 (0) | 60,000 | 12,000 | 48,000 |
| creator-2 | 2025-02 | 0 (0) | 60,000 (1) | -60,000 | 0 | -60,000 |
| creator-2 | 2025-03 | 60,000 (1) | 0 (0) | 60,000 | 12,000 | 48,000 |
| creator-3 | 2025-02 | 120,000 (1) | 0 (0) | 120,000 | 24,000 | 96,000 |
| creator-3 | 2025-03 | 0 (0) | 0 (0) | 0 | 0 | 0 |

운영자 기간 집계도 확인했다. 2025-03은 120,000 / 48,000 / 0 = **168,000**, 2025-01~03은 120,000 / 48,000 / 96,000 = **264,000**이다. 후자가 월별 합(252,000)과 다르다는 점이 Task 5·7의 핵심 주제다.
