# Task 7.7 — AI 활용 내역 명세

부모: [`task-7-readme-submission-spec.md`](./task-7-readme-submission-spec.md) · 의존 없음 · 10분

원본 과제가 명시적으로 요구하는 항목이다.

## 담을 내용

**무엇에 썼는지, 무엇을 사람이 판단했는지, 무엇이 AI 때문에 좋아졌는지** 세 가지를 적는다.

## 어디에 썼나

| 단계 | 활용 |
| --- | --- |
| 계획 | Task별 계획 문서 작성, 범위·전략 검토 |
| 명세 | 서브태스크 단위 구현 명세 작성 |
| 검수 | 계획·명세 교차 검토, 논리 모순 적발 |
| 구현 | 코드 작성, 테스트 작성 |
| 검증 | 시드 데이터의 정산 재현성 계산 검산 |

`docs/plan/`과 `docs/spec/` 아래 문서가 그 산출물이다. 링크로 언급한다.

## 교차 검토를 썼다

서로 다른 모델로 같은 문서를 두 번 검토했다. 한쪽이 놓친 것을 다른 쪽이 잡은 사례를 **구체적으로** 적는다.

- **쓰기 어댑터 부재.** Task 2가 만드는 포트는 조회 4개뿐인데 Task 4는 저장과 ID 조회가 필요했다. 11개 섹션 검수가 놓친 구현 블로커였다.
- **순환 의존.** Task 4가 Task 5의 접근 정책을 호출하는데 Task 5는 Task 4의 전역 예외 처리기를 의존했다.
- **테스트 소유권 중복.** 같은 시나리오를 두 Task가 각자 단언하고 있었다.

"AI를 썼다"보다 **"AI로 무엇을 잡았다"**가 정보량이 크다.

## 사람이 판단한 것

AI 추천을 그대로 받지 않고 뒤집거나 확정한 지점을 적는다.

- 인덱스 컬럼 순서를 뒤집자는 제안을 **철회**했다. 두 조회 경로가 상반된 선행 컬럼을 원한다는 것이 뒤늦게 드러났다.
- 운영자 집계를 단일 구간으로 할지 월별 합산으로 할지는 정책 판단이라 사람이 정했다.
- 범위 확장 제안을 3시간 예산 기준으로 반려했다.

## 검산에 썼다

시드 17행이 기대 정산표를 재현하는지 계산으로 검산했다. 손으로 하면 6개 행 × 7개 값을 검토해야 하고 실수가 난다. **운영자 1~3월이 월별 합(252,000)이 아니라 264,000이라는 것도 이 검산에서 확인했다.**

## 한계

AI가 만든 첫 계획에는 순환 의존과 소유권 중복이 있었다. 문서를 각각 보면 완결돼 보였고 **세트로 놓고 봐야 드러났다.** 검토 없이 받았으면 구현 중에 막혔을 것이다.

이 한 줄이 "AI를 어떻게 쓰는가"에 대한 답이다.

## 완료 기준

1. 단계별 활용이 표로 있다.
2. 교차 검토로 잡은 것이 구체적으로 3건 이상 있다.
3. 사람이 판단하거나 뒤집은 지점이 있다.
4. 한계가 솔직하게 적혀 있다.
