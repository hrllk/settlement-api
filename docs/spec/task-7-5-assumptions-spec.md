# Task 7.5 — 가정과 이탈 근거 21항 명세

부모: [`task-7-readme-submission-spec.md`](./task-7-readme-submission-spec.md) · 의존 Task 6 · 30분

README에서 가장 긴 절이고 배점이 가장 큰 절이다. 원본 과제가 "가정, 설계 이유, 미구현 범위"를 명시적으로 요구한다.

## 순서가 곧 우선순위다

1번을 맨 위에 둔다. 나머지는 성격별로 묶는다.

## 1. 운영자 기간 집계는 월별 정산의 합이 아니다 (최우선)

**이것만 놓치면 나머지 20항이 다 있어도 감점된다.**

평가자가 두 API를 돌리면 creator-2의 1~3월이 운영자 조회에서 48,000원, 월별 조회 세 번의 합으로는 36,000원으로 갈린다. 전체 합계로는 264,000 대 252,000이다.

원인을 수식으로 보인다.

```
단일 구간:  (60,000 + 60,000) − 60,000 = 60,000  → 수수료 12,000 → 48,000
월별 합산:   1월 48,000
            2월 순 −60,000 → 수수료 0 → −60,000
            3월 48,000
            합계 36,000
```

12,000원 차이는 2월의 음수 순 판매액에 **수수료 0원 제한**이 걸려 1월에 이미 뗀 수수료가 상쇄되지 않기 때문이다.

단일 구간을 택한 이유도 적는다. 월별 합산은 음수 월마다 제한이 반복 적용되어 크리에이터에게 불리하고 설명하기 어렵다. 단일 구간은 계산기를 기간만 바꿔 재사용하므로 순수 계산기 설계와 맞는다.

**문서 없이 이 동작을 보면 버그다.** 이 절의 존재 이유가 그것이다.

## 원본 과제 이탈 (2~4)

2. **반열린 구간 채택.** `말일 23:59:59`는 1초 미만 구간을 누락한다.
3. **초과 환불 거부 규칙 추가.** 원본에 없다. 누적 합계가 원결제액을 넘으면 409.
4. **취소 초기 데이터를 직접 정의.** 금액·귀속월은 과제 서술에서, 시각은 10:00 KST로 고정.

## 계산 정책 (5~7)

5. **수수료는 0으로 막고 정산 예정액은 음수를 허용한다.** 둘은 같은 종류의 수가 아니다. 수수료는 플랫폼이 매출에 부과하는 값이라 매출이 음수면 부과할 대상이 없다. 정산 예정액은 실제 채권·채무라 음수가 "크리에이터가 돌려줄 금액"이라는 의미를 갖는다.
6. **금액은 원 단위 `long`이고 수수료는 버림이다.** 양수 구간에서 `long` 나눗셈의 절단이 곧 버림이다. 순 판매액 33,333원이면 수수료 6,666원(실제 6,666.6).
7. **빈 월은 404가 아니라 200 + 전 항목 0이다.**

## 접근 경계 (8~10)

8. **액터 헤더는 실제 인증이 아니다.** `X-Actor-Id: admin-1`이라고 쓰면 그냥 운영자가 된다. 토큰도 서명도 검증하지 않는다. 과제가 명시적으로 허용한 단순화다.
9. **판매·취소 등록을 ADMIN으로 제한했다.** 원본에 명시가 없다. 크리에이터가 자기 강의의 판매를 임의로 등록할 수 있으면 정산을 스스로 부풀릴 수 있다.
10. **`RefundAmountExceeded`를 409로 뒀다.** 요청 형식이 아니라 자원 상태와의 충돌이다. 400으로 두면 Bean Validation 실패와 구분되지 않는다.

## 검증하지 않는 것 (11~14)

11. **취소 동시성을 보장하지 않는다.** 같은 판매에 취소 두 건이 동시에 오면 합계 검사를 둘 다 통과할 수 있다. 실무라면 판매 행에 `@Version`을 두거나 `SELECT ... FOR UPDATE`로 막을 지점이다.
12. **취소 시각이 결제 시각보다 이른 경우를 검증하지 않는다.** 과거로 소급된 취소가 들어갈 수 있다.
13. **ADMIN이 임의의 `paidAt`으로 과거 판매를 등록할 수 있다.** 시드 재현에 필요하지만, 이미 마감된 달의 정산을 사후에 바꿀 수 있다는 뜻이다.
14. **조회 기간 길이에 상한이 없다.** 10년 구간도 받는다.

## 설계 선택 (15~18)

15. **집계를 DB로 내리지 않고 순수 계산기를 택했다.** 기간이 길면 해당 구간 자료가 전부 메모리에 올라온다. 7건 기준에서 문제없고 설명 가능성을 우선했다.
16. **운영자 집계가 크리에이터마다 포트를 부른다 (N+1).** 3명이라 무의미하다. 포트 계약을 "`creatorId` 항상 필수"로 단순하게 유지하기 위한 선택이다. 크리에이터가 수천 명이면 다시 볼 지점이다.
17. **인덱스 컬럼 순서에서 두 조회 경로가 상반된 선행 컬럼을 원한다.** 특히 `findCancelsBySaleIds`는 시간 조건이 없어 `sale_id` 선행이 필요하다.
18. **식별자를 타입 래퍼 없이 `String`으로 뒀다.** 새 판매 ID는 서버 생성 UUID이며 시드의 `sale-1` 형태는 형식 제약이 아니다.

## 운영 관점 (19~20)

19. **`ddl-auto=create-drop`은 기동할 때마다 스키마를 새로 만든다.** 인메모리 H2 전용이며 운영 DB에 그대로 쓰면 데이터가 사라진다.
20. **H2 콘솔이 인증 없이 `/h2-console`에 열려 있다.** 채점 편의를 위한 설정이다. 운영 프로파일에서는 반드시 꺼야 한다.

## 검증 (21)

21. **커버리지 감사 표.** Task 6.4의 `docs/coverage-audit.md`를 여기 싣는다. 테스트가 다섯 Task에 흩어져 있어 이 표가 없으면 평가자가 커버리지를 확인할 수 없다. 어느 시나리오를 어느 파일이 단언하는지 22행으로 보인다.

## 추가한 테스트 케이스와 이유

원본 과제가 가산점을 건 항목이다. Task 3이 시드에 없는 픽스처로 추가한 케이스를 나열하고 각각을 왜 넣었는지 한 줄씩 적는다. 경계 3방향(시작 포함 / 종료 포함 / 종료 배제)이 각각 다른 잘못된 구현을 잡는다는 설명을 포함한다.
