# Task 3 — 정산 도메인 계산 구현: 검토 계획

## 목표

Spring과 데이터베이스 없이 동작하는 순수 정산 계산기를 만든다. 판매·취소 원본 자료를 입력받아 정산 요약과 판매별 환불 상태를 산출하는 것까지가 범위이며, API와 영속성은 포함하지 않는다.

## 병렬 진행 근거

`tasks.json`의 의존성은 `[1]`이지만 실제 결합은 루트 패키지 경로 하나뿐이다. 이 작업의 산출물은 Spring 컨텍스트와 JPA를 참조하지 않으므로 Task 1의 부트스트랩 완료를 기다리지 않고 병렬로 진행한다.

**Task 2는 Task 1과 Task 3 양쪽 뒤에 온다.** 빌드 스크립트와 `application.yml`은 Task 1이 주고, `SettlementQueryPort` 인터페이스와 `SaleData` / `CancelData` 값 타입은 Task 3가 준다. Task 2가 포트 구현체를 만들려면 둘 다 있어야 한다. `tasks.json`에는 Task 2의 의존성이 `[1]`로만 적혀 있어 이 순서가 드러나지 않는다.

이 작업을 먼저 여는 이유는 설계 판단이 전부 여기 몰려 있기 때문이다. 이중 집계 기준, KST 경계, 음수 순 판매액 정책이 틀리면 Task 5와 Task 6이 다시 짜인다. Task 2와 Task 4는 기계적이다.

## 포함 범위

- 정산 기간 `SettlementPeriod` — 연월(`2025-03`)과 시작일~종료일 두 입력을 KST 반열린 구간으로 정규화한다.
- 정산 요약 `SettlementSummary` — 총 판매액, 환불액, 순 판매액, 수수료, 정산 예정액, 판매 건수, 취소 건수.
- 환불 상태 `RefundStatus` — 판매별 취소 금액 합계에서 `NONE` / `PARTIAL` / `FULL`을 산출한다.
- 수수료 정책 `FeePolicy` — 고정 20%를 인터페이스 뒤에 둔다.
- 정산 계산기 `SettlementCalculator` — 원본 판매·취소 자료에서 요약을 산출한다.
- 조회 아웃바운드 포트 `SettlementQueryPort` — 인터페이스 선언만 둔다.
- 위 전부에 대한 단위 테스트.

## 제외 범위

- JPA 엔티티, 리포지토리, `SettlementQueryPort` 구현체 — Task 2
- 컨트롤러, 요청·응답 DTO, 전역 예외 처리기 — Task 4, Task 5
- 초과 환불 거부 — 취소 등록 시점의 규칙이므로 Task 4에 둔다
- 수수료율 이력 테이블, 정산 상태 전이, CSV 내보내기 — 명시적 제외 범위

취소 3건은 원본 과제에 없어 직접 정의했다. 금액과 귀속 월은 `tasks.json`이 확정한 값이고, 구체 일자는 원본의 "3월 취소" / "2월 초 취소" 서술 안에서 임의로 고정했다. 근거는 README에 남긴다.

**이 10건이 초기 시드 데이터의 전부다.** 아래 추가 테스트 케이스는 시드에 넣지 않는다. 넣으면 원본 과제가 명시한 creator-1의 3월 기대값 120,000원이 깨진다.

### 판매별 환불 상태 기대값

| 판매 | 원결제 | 취소 합계 | 환불 상태 |
|---|---|---|---|
| sale-1, sale-2, sale-6, sale-7 | — | 0 | `NONE` |
| sale-3 | 80,000 | 80,000 | `FULL` |
| sale-4 | 80,000 | 30,000 | `PARTIAL` |
| sale-5 | 60,000 | 60,000 | `FULL` |

환불 상태는 **기간 필터를 적용하지 않는다.** 그 판매에 연결된 모든 취소를 본다. sale-5는 1월 판매이고 취소는 2월인데, 1월 판매 목록을 조회해도 환불 상태는 `FULL`이어야 한다. 정산 금액 집계만 기간 기준으로 나뉘고 환불 상태는 나뉘지 않는다.

### 월별 정산 기대값

| 크리에이터 | 월 | 총 판매(건) | 환불(건) | 순 판매 | 수수료 | 정산 예정 |
|---|---|---|---|---|---|---|
| creator-1 | 2025-03 | 260,000 (4) | 110,000 (2) | 150,000 | 30,000 | 120,000 |
| creator-2 | 2025-01 | 60,000 (1) | 0 (0) | 60,000 | 12,000 | 48,000 |
| creator-2 | 2025-02 | 0 (0) | 60,000 (1) | -60,000 | 0 | -60,000 |
| creator-2 | 2025-03 | 60,000 (1) | 0 (0) | 60,000 | 12,000 | 48,000 |
| creator-3 | 2025-02 | 120,000 (1) | 0 (0) | 120,000 | 24,000 | 96,000 |
| creator-3 | 2025-03 | 0 (0) | 0 (0) | 0 | 0 | 0 |

creator-1의 2025-03은 원본 과제가 명시한 기대값과 일치한다.

creator-2의 2025-02는 판매 없이 1월 판매분의 취소만 있는 달이다. 순 판매액이 음수가 되어 수수료 0원 제한이 실제로 걸리는 유일한 케이스이므로 최우선 테스트로 둔다.

### 운영자 기간 집계 기대값

| 기간 | creator-1 | creator-2 | creator-3 | 전체 합계 |
|---|---|---|---|---|
| 2025-03-01 ~ 2025-03-31 | 120,000 | 48,000 | 0 | 168,000 |
| 2025-01-01 ~ 2025-03-31 | 120,000 | 48,000 | 96,000 | 264,000 |

**주의: 이 표는 위 월별 표의 단순 합이 아니다.** creator-2를 월별로 더하면 48,000 + (-60,000) + 48,000 = 36,000이지만 기간 집계는 48,000이다. 12,000원 차이는 월별 합산일 때 2월의 음수 순 판매액에 수수료 0원 제한이 걸려 1월에 이미 뗀 수수료가 상쇄되지 않기 때문이다. 확정된 전제 8을 참조한다.

## 확정된 전제

1. **기간 경계는 반열린 구간이다.** `[시작일 00:00, 종료일 다음 날 00:00)` KST. 원본 과제의 `말일 23:59:59`는 초 미만 구간이 누락되므로 의도적으로 이탈한다. README에 근거를 남긴다.

2. **시간 값은 `Instant`로 다룬다.** `SaleData.paidAt`과 `CancelData.cancelledAt`은 UTC 순간이다. KST 연월·일자를 `Instant` 반열린 구간으로 바꾸는 책임은 전부 `SettlementPeriod`에 있고, 계산기는 시간대를 모른다. 시간대 지식이 클래스 하나에만 산다. `LocalDateTime`은 쓰지 않는다 — 값이 KST인지 UTC인지 코드에 안 남아 sale-5(`2025-01-31T23:30+09:00` = `2025-01-31T14:30Z`)가 1월 대신 2월로 귀속되는 사고의 전형적 원인이다.

3. **판매와 환불의 집계 기준이 다르다.** 판매는 `paidAt`, 환불은 `cancelledAt`으로 각각 귀속 기간을 판단한다. 금액뿐 아니라 **건수도 같은 기준을 따른다** — creator-2의 2025-02는 판매 건수 0, 취소 건수 1이다.

4. **금액은 원 단위 `long`이다.** 부동소수점을 쓰지 않는다.

5. **수수료 계산은 음수 판정을 먼저 한다.** 순서가 곧 정책이다.
   ```
   if (net <= 0) return 0;
   return net * bp / 10000;   // bp = 2000 (20%)
   ```
   순서가 중요한 이유는 정책이다. 음수 매출에는 수수료를 부과하지 않는다. 판정을 나중에 하면 `-60,000`에서 `-12,000`이 나와 플랫폼이 크리에이터에게 수수료를 돌려주는 셈이 된다. 양수 구간에서 `long` 나눗셈의 절단이 곧 버림이므로 이것이 버림 정책이기도 하다.

6. **정산 예정액 = 순 판매액 − 수수료.** 음수면 그대로 반환한다. 크리에이터가 플랫폼에 돌려줘야 할 환불 부담액으로 해석한다.

   전제 5와의 비대칭을 명시한다. 수수료는 0으로 막고 정산 예정액은 음수를 허용한다. 수수료는 플랫폼이 매출에 부과하는 값이라 매출이 음수일 때 부과할 대상이 없다. 정산 예정액은 실제 채권·채무 금액이라 음수가 "크리에이터가 돌려줄 금액"이라는 의미를 갖는다. 둘은 같은 종류의 수가 아니다.

7. **빈 월은 전 항목 0원 정상 응답이다.** 404가 아니다. 원본 과제의 "0원 응답 또는 처리 방침 일관성 확인"에 따라 0원으로 통일한다.

8. **운영자 기간 집계는 기간 전체를 단일 정산 구간으로 계산한다.** 월별로 계산해 합산하지 않는다. 월별 합산 방식은 음수 월마다 수수료 0원 제한이 반복 적용되어 크리에이터에게 불리해지고 설명하기 어렵다. 단일 구간 방식은 `SettlementCalculator`를 기간만 바꿔 그대로 재사용할 수 있어 "순수 계산기" 설계와도 맞는다.

9. **수수료율은 인터페이스 뒤에 둔다.** `FeePolicy` + `FixedRateFeePolicy(2000bp)`. 이력 테이블과 시점별 요율 적용은 만들지 않는다. 원본 과제의 "변경 가능성을 설계에 반영하면 가산점"을 이력 관리 없이 충족한다.

10. **환불 상태는 저장하지 않고 매번 계산한다.** 취소 금액 합계가 0이면 `NONE`, 원결제 **이상이면** `FULL`, 그 사이면 `PARTIAL`이다. 초과 등록은 Task 4가 거부하지만 Task 4는 나중 태스크이므로 `>=`로 받아 분기를 닫는다. "방어하지 않는다"는 코드로 표현할 수 없다.

11. **계산기는 로그를 남기지 않는다.** 로깅을 넣으면 도메인에 SLF4J 의존성이 딸려온다. PRD가 요구한 "조회 성공과 도메인 실패 로그"는 application 유스케이스에서 남긴다.

## 값 타입 정의

계산기가 받는 입력 타입이다. JPA 엔티티가 아니며 계산에 필요한 필드만 갖는다. `courseId`, `studentId`는 계산에 쓰이지 않으므로 넣지 않는다.

```java
record SaleData  (String saleId, String creatorId, long amount, Instant paidAt) {}
record CancelData(String cancelId, String saleId, long amount, Instant cancelledAt) {}
```

식별자는 `String`으로 둔다. `CreatorId` / `SaleId` 타입 래퍼를 만들면 타입 안전성은 오르지만 3시간 예산에서 클래스 2개와 변환 코드가 늘어난다. 원본 데이터의 식별자가 `creator-1` 같은 문자열이라 래핑 이득도 작다. 이 선택을 README에 한 줄로 남긴다.

`CancelData`에 `creatorId`가 없는 것은 의도적이다. 아래 포트 계약에서 취소를 항상 크리에이터로 좁혀 조회하므로 값 자체가 귀속 정보를 들 필요가 없다.

## 포트 계약

```java
public interface SettlementQueryPort {
    List<SaleData>   findSales  (Instant fromInclusive, Instant toExclusive, String creatorId);
    List<CancelData> findCancels(Instant fromInclusive, Instant toExclusive, String creatorId);
    List<CancelData> findCancelsBySaleIds(Collection<String> saleIds);
    List<String>     findAllCreatorIds();
}
```

- **`creatorId`는 항상 필수다.** 전체 크리에이터를 한 번에 긁는 경로는 두지 않는다. 운영자 기간 집계는 `findAllCreatorIds()`로 목록을 받은 뒤 크리에이터마다 계산기를 한 번씩 돌린다. 크리에이터가 3명이라 N+1이 문제되지 않고, 조회 경로가 하나뿐이라 계약이 단순해진다.
- **`findAllCreatorIds()`가 따로 필요한 이유는 creator-3 때문이다.** 3월에 판매도 취소도 없는 크리에이터를 운영자 목록에 0원으로 넣으려면 판매·취소 자료만으로는 존재를 알 수 없다.
- **`findCancelsBySaleIds()`는 환불 상태 전용이다.** 환불 상태는 기간 필터를 적용하지 않으므로(기준표의 환불 상태 절 참조) `cancelledAt` 창 조회로는 산출할 수 없다. sale-5는 1월 판매인데 취소가 2월 3일이라 `[1/1, 2/1)` 창에 안 잡힌다. 이 메서드가 없으면 1월 판매 목록에서 sale-5가 `FULL`이 아니라 `NONE`으로 나온다. 판매 목록 조회(Task 4)가 이 경로를 쓴다.
- **어떤 메서드도 `null`을 반환하지 않는다.** 결과가 없으면 빈 리스트다. 계산기는 `null` 방어를 하지 않으며, 이 계약 위반은 구현체의 결함이다.
- 웹 어댑터는 연월·일자를 **`String`으로 받아** `SettlementPeriod` 팩토리에 그대로 넘긴다. `@PathVariable YearMonth`로 바인딩하면 Spring이 `MethodArgumentTypeMismatchException`을 먼저 던져 `InvalidSettlementPeriod`가 걸리지 않는다. 전역 처리기가 그 예외도 잡으면 되긴 하지만, `2025-13`의 거부는 도메인 규칙이므로 도메인이 판정하게 두는 편이 PRD의 "비즈니스 규칙은 application/domain에 둔다"와 맞고 오류 응답 형식도 하나로 유지된다.

## 책임 분담

운영자 집계는 두 태스크에 걸쳐 있다. 경계를 명시한다.

| 책임 | 소유 |
|---|---|
| 기간 단일 구간에서 크리에이터 1명의 정산 요약 산출 | **Task 3** `SettlementCalculator` |
| 크리에이터 목록 조회, 반복 호출, 결과 목록 조립, 전체 합계 | **Task 5** application 유스케이스 |
| 판매별 환불 상태 산출 | **Task 3** `RefundStatus` |
| 판매 목록 응답에 환불 상태 결합 | **Task 4** application 유스케이스 |

계산기는 크리에이터별 그룹핑을 하지 않는다. 입력으로 받은 판매·취소가 이미 한 크리에이터의 것이라고 가정한다.

## 완료 기준

- 계산기 단위 테스트가 Spring 컨텍스트와 H2 없이 통과한다.
- 기준표의 월별 6개 행과 환불 상태 4개 행을 명시적으로 단언한다.
- 운영자 기간 표는 **크리에이터별 정산 예정액 3개 값**(120,000 / 48,000 / 0, 그리고 1~3월 구간의 120,000 / 48,000 / 96,000)을 계산기 단위 테스트로 단언한다. 목록 조립과 전체 합계(168,000 / 264,000)는 Task 5가 단언한다.
- 시간·외부 서비스·테스트 실행 순서에 의존하지 않는다. 현재 시각을 읽지 않는다.
- 아래 추가 케이스가 함께 통과한다.

## 추가 테스트 케이스

**단위 테스트 전용 픽스처다. 초기 시드 데이터에 넣지 않는다.** 어떤 케이스를 왜 추가했는지 README에 기술한다.

| 케이스 | 입력 | 기대 |
|---|---|---|
| 수수료 버림 | 순 판매액 33,333 | 수수료 6,666 (실제 6,666.6), 정산 26,667 |
| 동일 판매 다수 부분 취소 | 원결제 80,000에 30,000 + 20,000 | 환불 50,000, 취소 건수 2, 상태 `PARTIAL` |
| 다중 월 단일 구간 집계 | creator-2, 2025-01-01~2025-03-31 | 48,000 (36,000이 아님) |
| 시작 경계 포함 | `2025-03-01T00:00:00.000+09:00` 결제 | 3월에 귀속 |
| 종료 경계 포함 | `2025-01-31T23:59:59.999+09:00` 결제 | 1월에 귀속 |
| 종료 경계 배제 | `2025-02-01T00:00:00.000+09:00` 결제 | 1월에 **안** 들어가고 2월에 들어감 |
| 기간 밖 취소로 환불 상태 | sale-5 조회, 취소는 기간 밖 | `FULL` (기간 필터 미적용 확인) |
| 종료일이 시작일보다 이름 | 2025-03-31 ~ 2025-03-01 | `InvalidSettlementPeriod` |
| 잘못된 연월 형식 | `2025-13`, `2025/03`, `""`, `null` | `InvalidSettlementPeriod` |
| 포트가 빈 리스트 반환 | 판매 0건, 취소 0건 | 전 항목 0원 요약 |

경계 케이스가 셋인 이유는 각각 다른 것을 잡기 때문이다.

- **시작 경계 포함**은 하한이 열려 있는 구현(`> from`)을 잡는다.
- **종료 경계 포함(`23:59:59.999`)**은 원본 과제 문구를 곧이곧대로 옮긴 구현(`<= 말일 23:59:59`)을 잡는다. `.999`가 `23:59:59`보다 크므로 그 구현에서는 배제된다.
- **종료 경계 배제(`2월 1일 00:00`)**는 상한을 닫은 구현(`<= to`)을 잡는다. 앞의 두 케이스는 상한을 나노초 최대값까지 닫아도 통과하므로 이것 없이는 반열린 구간이 검증되지 않는다.

반열린 구간은 이 태스크의 핵심 설계 판단이므로 세 방향을 다 잠근다.

`InvalidSettlementPeriod`는 이 작업에서 도메인 예외로 정의만 하고, HTTP 응답 변환은 Task 4의 전역 예외 처리기에서 한다.

## 후속 작업으로 넘기는 항목

### `tasks.json` 수정 필요 (main에서 적용)

1. **Task 5의 `dependencies`에 `4`를 추가한다.** 전역 예외 처리기가 Task 4에 있는데 Task 5가 `InvalidSettlementPeriod`를 던진다. 현재 의존성은 `[2, 3]`이라 Task 5를 먼저 끝내면 잘못된 연월 요청이 처리기 없이 500 스택트레이스로 나간다. Task 4 안에서도 전역 예외 처리기를 먼저 만든다.
2. **Task 5 상세의 "건수"를 "판매 건수와 취소 건수"로 고친다.** 원본 과제는 두 개를 요구한다.
3. **Task 2의 `dependencies`에 `3`을 추가한다.** 포트 구현체가 Task 3의 인터페이스와 값 타입에 의존한다.

### Task 2에서 확인할 것

4. **엔티티의 시간 컬럼을 `Instant`로 매핑한다.** 전제 2에 맞춘다.
5. **인덱스는 `tasks.json`의 현행 정의를 그대로 둔다.** 검토 중에 `(course_id, paid_at)`을 `(paid_at, course_id)`로 뒤집자는 제안이 나왔으나 철회한다. 두 조회 경로가 상반된 컬럼 순서를 원하기 때문이다 — 크리에이터별 조회는 `course_id` 선행이, 운영자 기간 조회는 `paid_at` 선행이 유리하다. 한쪽으로 뒤집으면 다른 쪽이 손해다. 데이터가 7건이라 실측 차이가 0이므로 인덱스 하나를 유지하고, **두 경로가 다른 순서를 원한다는 관찰만 README에 남긴다.** 실제 트래픽이 있다면 인덱스를 하나 더 두거나 커버링 인덱스를 검토할 지점이라는 설명이 붙으면 그 자체로 설계 이해의 신호가 된다.

### Task 5에서 확인할 것

6. **역할 매트릭스를 정의한다.** `X-Actor-Role`은 헤더라 누구나 바꾼다. 어느 엔드포인트가 어느 역할을 요구하는지가 현재 어느 문서에도 없다. 최소 두 가지를 막아야 한다.
   - 크리에이터가 운영자 기간 집계를 호출해 전체 매출을 보는 것
   - 크리에이터 A가 경로 파라미터를 B로 바꿔 타인 정산을 보는 것 (`X-Actor-Id`와 경로 `creatorId` 일치 검증)

### Task 7 README에 남길 것

7. **운영자 기간 집계가 월별 정산의 합이 아니라는 점 (최우선).** 평가자가 두 API를 돌리면 creator-2의 1~3월이 운영자 조회에서 48,000원, 월별 조회 세 번의 합으로는 36,000원으로 갈린다. **문서가 없으면 버그로 읽힌다.** 12,000원 차이의 원인(2월 음수 순 판매액에 수수료 0원 제한이 걸려 1월 수수료가 상쇄되지 않음)과 단일 구간 방식을 택한 근거를 함께 적는다. 전제 8의 최대 리스크는 정책 자체가 아니라 미문서화다.
8. 원본 과제 대비 이탈 2건 — 반열린 구간 채택 근거, 초과 환불 거부 규칙 추가.
9. 취소 초기 데이터를 직접 정의한 근거.
10. 수수료는 0으로 막고 정산 예정액은 음수를 허용하는 비대칭의 근거 (전제 6).
11. 집계를 DB로 내리지 않고 순수 계산기를 택한 이유와 그 한계. 기간이 길면 해당 구간 판매·취소가 전부 메모리에 올라온다. 과제 데이터 7건 기준에서는 문제가 없고, 설명 가능성을 우선한 선택이다.
12. 인덱스 컬럼 순서에서 크리에이터별 조회와 운영자 기간 조회가 상반된 선행 컬럼을 원한다는 관찰 (후속 항목 5).
13. 식별자를 타입 래퍼 없이 `String`으로 둔 근거.
14. 조회 기간 길이에 상한을 두지 않았다는 가정.
15. 단순 액터 헤더가 실제 인증이 아니라는 점.
16. 추가한 테스트 케이스 목록과 각각을 추가한 이유. 원본 과제가 명시적으로 가산점을 건 항목이다.
17. 정산 상태 전이를 나중에 붙일 경우의 경로. `SettlementSummary`가 영속화되지 않는 값 타입이므로 정산 스냅샷 엔티티를 새로 두면 된다. 지금 구조가 막다른 길이 아니라는 점을 한 줄로 남긴다.

### Task 6과의 테스트 분담

18. **Task 3가 계산기 단언을 전부 소유한다.** 기준표 월별 6행, 환불 상태 4행, 크리에이터별 기간 정산액, 추가 케이스 10건이 여기에 있다. Task 6은 이것을 다시 단언하지 않는다.
19. **Task 6은 세 가지만 추가한다.** 누적 초과 환불 거부(Task 4 규칙이라 계산기에 없음), 운영자 응답의 목록 조립과 전체 합계(Task 5 책임), HTTP 통합 흐름 1건. `tasks.json` Task 6 상세가 나열한 항목 중 3월 기대 금액·부분 환불·월 경계·빈 월·잘못된 기간은 Task 3에서 이미 잠기므로 통합 레벨에서 반복하지 않는다.

### 이 작업에서 검증하지 않는 것

20. 초과 환불 거부의 누적 합계 판정은 Task 4에서 구현한다. 계산기는 이미 등록된 취소를 그대로 집계할 뿐 유효성을 검증하지 않는다.
