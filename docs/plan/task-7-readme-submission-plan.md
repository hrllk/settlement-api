# Task 7 — README와 제출 전 점검: 검토 계획

## 목표

평가자가 5분 안에 실행하고, 설계 판단의 근거를 코드를 읽지 않고도 알 수 있게 한다.

## 왜 이 태스크가 가장 큰 위험인가

이 프로젝트에는 **문서가 없으면 버그로 읽히는 동작이 하나 있다.** 운영자 기간 집계가 월별 정산의 합이 아니다. creator-2의 1~3월이 운영자 조회에서 48,000원, 월별 조회 세 번의 합으로는 36,000원으로 갈린다. 평가자가 두 API를 돌리면 반드시 본다.

정책 자체는 Task 3에서 검토를 거쳐 확정했다. **최대 리스크는 정책이 아니라 미문서화다.** README 최우선 항목으로 둔다.

## 가정과 이탈 근거 (전량)

Task 3 계획의 후속 항목과 Task 2·4·5에서 새로 생긴 판단을 합쳤다.

1. **운영자 기간 집계가 월별 합이 아니다.** 12,000원 차이의 원인과 단일 구간을 택한 근거. **최우선.**
2. **반열린 구간 채택.** 원본 과제의 `말일 23:59:59`는 초 미만이 누락된다.
3. **초과 환불 거부 규칙 추가.** 원본에 없다.
4. **취소 초기 데이터를 직접 정의했다.** 금액·귀속월은 과제 서술에서, 구체 시각은 10:00 KST로 고정.
5. **수수료는 0으로 막고 정산 예정액은 음수를 허용한다.** 둘은 같은 종류의 수가 아니다.
6. **식별자를 타입 래퍼 없이 `String`으로 뒀다.**
7. **조회 기간 길이에 상한이 없다.**
8. **액터 헤더는 실제 인증이 아니다.** 헤더에 쓴 값이 곧 신원이다.
9. **판매·취소 등록을 ADMIN으로 제한했다.** 원본에 명시가 없다. 크리에이터가 자기 정산을 부풀릴 수 있어 운영자로 좁혔다.
10. **`RefundAmountExceeded`를 409로 뒀다.** 요청 형식이 아니라 자원 상태와의 충돌이다.
11. **취소 동시성을 보장하지 않는다.** 같은 판매에 동시 취소 두 건이 합계 검사를 둘 다 통과할 수 있다. 실무라면 행 잠금이나 버전 컬럼으로 막을 지점.
12. **인덱스 컬럼 순서에서 두 조회 경로가 상반된 선행 컬럼을 원한다.** 특히 `findCancelsBySaleIds`는 시간 조건이 없어 `sale_id` 선행이 필요하다. 7건 규모라 현행을 유지하고 관찰만 남긴다.
13. **집계를 DB로 내리지 않고 순수 계산기를 택했다.** 기간이 길면 해당 구간 자료가 전부 메모리에 올라온다. 설명 가능성을 우선했다.
14. **추가한 테스트 케이스 목록과 각각의 이유.** 원본 과제가 가산점을 건 항목이다.
15. **정산 상태 전이 확장 경로.** `SettlementSummary`가 영속화되지 않는 값 타입이므로 스냅샷 엔티티를 새로 두면 된다.
16. **새 판매의 ID는 서버가 생성한 UUID다.** 시드의 `sale-1` 형태는 사람이 읽기 좋은 고정값일 뿐 형식 제약이 아니다. 응답 예시에 두 형태가 같이 보이므로 한 줄 설명을 붙인다.
17. **취소 시각이 결제 시각보다 이른 경우를 검증하지 않는다.** 등록 순서를 강제하지 않으므로 과거로 소급된 취소가 들어갈 수 있다. 실무라면 `cancelledAt >= paidAt`을 거부할 지점이다.
18. **ADMIN이 임의의 `paidAt`으로 과거 판매를 등록할 수 있다.** 시드 재현에 필요한 기능이지만, 이미 마감된 달의 정산을 사후에 바꿀 수 있다는 뜻이다.
19. **`ddl-auto=create-drop`은 기동할 때마다 스키마를 새로 만든다.** 인메모리 H2 전용 설정이며 운영 데이터베이스에 그대로 쓰면 데이터가 사라진다.
20. **H2 콘솔이 인증 없이 `/h2-console`에 열려 있다.** 채점 편의를 위한 설정이다. 운영 프로파일에서는 반드시 꺼야 한다.
21. **커버리지 감사 결과.** Task 6.4가 대조한 소유권 표와, 어느 Task가 어느 시나리오를 단언하는지의 대응을 그대로 싣는다. 테스트가 여러 파일에 흩어져 있으므로 이 표가 없으면 평가자가 커버리지를 확인할 수 없다.

## 제출 전 클린 점검 (7.8)

| 항목 | 확인 |
|---|---|
| 클린 클론 | 임시 디렉터리에 clone 후 `./gradlew clean test` 통과 |

| 기동 | `./gradlew bootRun` 후 로그에 예외 없음 |

| 오류 포맷 | 모든 오류 응답이 `RFC 9457 problem+json` 한 가지 모양 |

**클린 클론 점검이 핵심이다.** 로컬에만 있고 커밋 안 된 파일에 의존하면 평가자 환경에서 깨진다. Task 1에서 실제로 겪은 문제다 — `.gitignore`의 `out/` 패턴이 `adapter/out` 소스 패키지를 삼켰고, `git add -n`으로 확인해서 잡았다.
