# Task 6 — 핵심 판단 시나리오 검증: 검토 계획

## 목표

Task 3·4·5가 각자 잠그지 못하는 것만 검증한다. 이미 단언된 숫자를 다시 단언하지 않는다.

## 테스트 소유권

이 계획의 핵심 판단이다. **Task 3이 계산기 단언을 전부 소유한다.**

| 검증 대상 | 소유 | 이유 |
|---|---|---|
| 월별 정산 6행 (3월 120,000, 부분 환불, 월 경계 음수, 빈 월) | Task 3 | 계산기 단위 테스트. Spring·H2 없이 돈다 |
| 환불 상태 4행 | Task 3 | 같음 |
| 잘못된 기간 거부 (`2025-13`, `2025/03`, 빈 값, 종료일 < 시작일) | Task 3 | `SettlementPeriod` 도메인 규칙 |
| 경계 3종 (시작 포함 / 종료 포함 / 종료 배제) | Task 3 | 같음 |
| 수수료 버림, 다중 부분 취소 | Task 3 | 같음 |
| 오류 상태 코드 변환 (404 / 409 / 403 / 400) | Task 4 | 전역 처리기 소유 |
| 접근 경계 4종, opt-in 가드 | Task 5 | 역할 매트릭스 소유 |
| 누적 초과 환불 거부 | Task 4 | 등록 규칙을 소유한 곳이 테스트도 소유한다 |
| 운영자 목록 조립과 전체 합계 | Task 5 | 유스케이스를 소유한 곳이 테스트도 소유한다 |
| **HTTP 통합 흐름 1건** | **Task 6** | 어느 Task도 혼자서는 배선 전체를 못 본다 |
| **커버리지 감사** | **Task 6** | 앞 Task들이 약속한 테스트를 실제로 썼는지 대조 |

원칙은 하나다. **규칙을 소유한 Task가 그 규칙의 테스트도 소유한다.** 그래야 각 Task가 혼자 완결되고, 머지 순서를 바꿔도 검증에 구멍이 안 생긴다. 초기 계획은 누적 초과 환불을 Task 4·6이, 운영자 합계를 Task 5·6이 둘 다 소유하고 있었다. 뿌리는 Task 3 계획서의 자기모순이다. 완료 기준은 "전체 합계는 Task 5가 단언한다"고 하는데 항목 19는 "Task 6이 추가한다"고 한다. 전자를 택했다.

PRD가 요구하는 "3월 계산, 부분 환불, 월 경계 취소, 판매 없는 월"은 **저장소 전체 기준의 커버리지 요구**이지 Task별 요구가 아니다. Task 3이 계산기 단위로 잠그면 충족된다. 같은 숫자를 두 파일에 박으면 시드를 바꿀 때 한쪽만 고치는 사고가 난다.

그래서 Task 6에 **커버리지 감사**를 넣는다. "각자 자기 것을 테스트한다"는 원칙의 유일한 약점은 한 Task가 약속을 안 지켜도 아무도 모른다는 것이다. 감사가 그 틈을 맡는다.

대신 **HTTP 통합 테스트를 강화한다.** 상태 코드 200만 보는 대신 실제 금액을 단언하게 해서, 계산기가 맞아도 컨트롤러·유스케이스 배선이 틀리면 잡히게 한다. 계산 정확성과 배선 정확성을 다른 계층에서 각각 한 번씩 검증하는 구조다.

- HTTP 통합 흐름 1건 (금액 단언 포함)
- 결정성 점검
- 커버리지 감사

## 제외 범위

위 소유권 표에서 Task 3·4·5로 표시된 전부.

## 확정된 전제

1. **기준표 상수는 Task 3이 만들고 Task 6은 재사용한다.** Task 3의 계산기 테스트가 이 상수의 첫 소비자이고 Task 6보다 한참 먼저 온다. Task 6이 "공용 픽스처를 만든다"고 하면 Task 3은 그때까지 자기 리터럴을 들고 있다가 나중에 갈아끼워야 한다. 순서가 거꾸로다. Task 6은 새로 만들지 않고 Task 3의 상수를 그대로 쓴다.

2. **시드와 픽스처를 분리한다.** `data.sql` 17행은 시드다. Task 3의 추가 케이스(33,333원 버림 등)는 픽스처이며 시드에 넣지 않는다. 넣으면 creator-1의 3월 기대값이 깨진다.

3. **Task 6이 만드는 테스트 중 H2를 쓰는 것은 HTTP 통합 1건뿐이다.** 저장소 전체로 보면 Task 1의 컨텍스트 기동 테스트와 Task 2의 시드 재현성 테스트도 H2를 쓴다. Task 6은 그 위에 하나만 더 얹는다.

4. **현재 시각을 읽지 않는다.** `Instant.now()`, `LocalDate.now()`를 테스트에서도 프로덕션 코드에서도 쓰지 않는다. 2025년 데이터라 실행 시점에 따라 결과가 흔들리면 안 된다.

5. **통합 테스트는 시드가 쓰지 않는 월에 데이터를 넣는다.** 시드는 2025년 1~3월만 쓴다. 통합 테스트는 **2025-06**을 쓰고 `@Transactional`로 롤백도 건다. 둘 다 건다.

   롤백만 믿지 않는 이유는 `DB_CLOSE_DELAY=-1` 때문이다. 인메모리 DB가 JVM 수명 내내 살아 있어서 롤백이 한 번이라도 새면 creator-1의 3월 기대값 120,000원이 조용히 틀어지고, 깨지는 건 이 테스트가 아니라 **다른 파일의 시드 기반 단언**이다. 원인을 찾기 가장 어려운 종류의 실패다. 월을 분리하면 롤백이 실패해도 아무것도 안 깨진다.

## HTTP 통합 흐름

한 건에 배선 전체를 태운다.

```
1. POST /api/sales                             ADMIN, paidAt = 2025-06-10 KST
   → 응답 본문에서 서버가 생성한 saleId(UUID)를 받는다
2. POST /api/sales/{saleId}/cancellations      ADMIN, 부분 취소
3. GET  /api/creators/{creatorId}/settlements/2025-06   본인 CREATOR
   → 1·2에서 넣은 금액이 총 판매액·환불액·순 판매액·수수료·정산 예정액에
     정확히 반영됐는지 단언한다. 200 확인으로 끝내지 않는다.
```

2단계가 1단계 응답의 `saleId`에 의존한다. Task 4가 생성 ID를 응답에 담지 않으면 이 테스트를 쓸 수 없다. Task 4 전제 5가 이것을 보장한다.

이 흐름이 잡는 것: 액터 헤더 해석 → 컨트롤러 배선 → 유스케이스 → 포트 → JPA → 계산기 → 응답 DTO. 어느 한 곳이 끊기면 실패한다.

- **각 Task가 약속한 테스트를 안 쓰면 아무도 모른다.** "자기 것은 자기가 테스트한다"의 유일한 약점이다. 6.4 커버리지 감사가 이 틈을 맡는다.
