## 핵심 테스트 10건

초기 데이터만으로는 안 걸리는 것들입니다. **각각이 다른 잘못된 구현을 잡습니다.**

| 케이스 | 무엇을 잡나 |
| --- | --- |
| **운영자 1~3월 264,000** | **월별 합산 구현을 잡는 유일한 테스트.** 2025-03만 보면 두 방식이 둘 다 168,000입니다 |
| 이상 미만 경계 3방향 | `<=`를 쓰면 다음 달 1일이 새고, `<`를 시작에 쓰면 1일이 빠집니다 |
| 누적 초과 환불 (30,000 → 60,000) | 단건 비교를 잡습니다. `amount > sale.amount()`만 보면 둘 다 통과해 90,000원이 환불됩니다 |
| 전액 환불 (합계 == 원결제) | `>=`면 전액 환불이 거부됩니다 |
| `Long.MAX_VALUE` 취소 | 오버플로를 잡습니다. `already + amount`는 음수가 되어 상한 검사를 통과합니다 |
| 수수료 버림 (33,333 → 6,666) | 반올림 구현을 잡습니다. 초기 데이터 금액은 전부 나누어떨어집니다 |
| 동일 판매 다수 부분 취소 | 취소를 하나만 읽는 구현을 잡습니다 |
| `to`가 종료일 포함 (하루 구간) | 3월 31일 데이터가 없어 `to=03-31`과 `to=04-01`이 같은 값을 냅니다 |
| 운영자 집계 쿼리 수 | N+1 회귀를 잡습니다. 크리에이터마다 조회해도 **결과값은 같아서** 다른 테스트가 못 잡습니다 |
| opt-in 가드 | `ActorContext`를 선언 안 한 핸들러를 잡습니다. 컴파일도 테스트도 통과하고 응답도 200인데 무방비로 열립니다 |

**첫 줄이 이 문서에서 가장 중요합니다.** 월별 합산으로 잘못 구현해도 2025-03 단독 조회는 정답이 나옵니다. 3월에는 음수 월이 없기 때문입니다.

마지막 두 건은 **"대상이 0개여도 통과"**할 수 있는 종류라, 각각 짝 테스트를 뒀습니다. `guardIsNotVacuous`가 핸들러 5개 이상을, `scannerReadsSources`가 소스 20개 이상을 실제로 보고 있는지 확인합니다.

## 결정성

| 검사 | 방법 | 결과 |
| --- | --- | --- |
| `now()` 호출 | `NoCurrentTimeUsageTest` (자동) | 0건 |
| 두 번 연속 실행 | `./gradlew cleanTest test` × 2 | 112건 / 112건, 동일 |
| 실행 순서 의존 | `@TestMethodOrder`·`@Order` | 0건 |
| 외부 서비스 | HTTP·브로커·외부 API | 없음. H2 인메모리뿐 |

`sale-5`의 값이 `data.sql`(UTC)과 `SettlementFixtures`(KST) 두 곳에 있습니다. 형식이 달라 한쪽에서 다른 쪽을 만들 수 없어, **초기 데이터를 바꾸면 두 곳을 다 고쳐야 합니다.**

계산기 픽스처의 추가 케이스를 `data.sql`에 넣지 않은 이유는 creator-1의 2025-03 기대값 120,000원이 깨지기 때문입니다. 그 값은 원본 과제가 명시한 숫자입니다. E2E는 아예 다른 달(2025-06)을 씁니다.
