| 판매·취소 API | 35 | 등록·취소, 애그리게이트 불변식, 오류 포맷, 인가 판정 |

**도메인 계산이 44건으로 가장 큽니다.** 금액이 맞는지를 Spring도 H2도 없이 잠그기 때문에, 위 계층들이 같은 숫자를 다시 단언하지 않아도 됩니다. API 테스트는 배선만 봅니다.

## 추가한 테스트 케이스

시드에 없는 픽스처로 넣은 것들입니다. 각각이 **다른 잘못된 구현**을 잡습니다.

| 케이스 | 무엇을 잡나 |
| --- | --- |
| 반열린 구간 경계 3방향 | 시작 포함 / 말일 23:59:59.999 포함 / 다음 달 1일 00:00 배제. `<=`를 쓰면 셋째가, `<`를 시작에 쓰면 첫째가 깨집니다 |
| 수수료 버림 (33,333 → 6,666) | 반올림 구현을 잡습니다. 시드 금액은 전부 나누어떨어져 이 케이스 없이는 안 걸립니다 |
| 동일 판매 다수 부분 취소 | 취소를 하나만 읽는 구현을 잡습니다 |
| 누적 초과 환불 (30,000 → 60,000) | 단건 비교를 잡습니다. `amount > sale.amount()`만 보면 둘 다 통과해 90,000원이 환불됩니다 |
| 전액 환불 (합계 == 원결제) | 부등호 하나짜리 실수를 잡습니다. `>=`면 전액 환불이 거부됩니다 |
| `Long.MAX_VALUE` 취소 | 오버플로를 잡습니다. `already + amount`로 쓰면 음수가 되어 상한 검사를 통과합니다 |
| 운영자 1~3월 264,000 | **월별 합산 구현을 잡는 유일한 테스트.** 2025-03만 보면 두 방식이 둘 다 168,000이다 |
| `to`가 종료일을 포함 (하루 구간) | 시드에 3월 31일 데이터가 없어 `to=03-31`과 `to=04-01`이 같은 값을 냅니다. 하루짜리 구간으로만 구분됩니다 |
| 운영자 집계 쿼리 수 | N+1 회귀를 잡습니다. 크리에이터마다 조회해도 **결과값은 같아서** 다른 테스트가 못 잡습니다 |
| opt-in 가드 | `ActorContext`를 선언 안 한 핸들러를 잡습니다. 컴파일도 테스트도 통과하고 응답도 200인데 무방비로 열립니다 |

## 커버리지 감사

"규칙을 소유한 Task가 그 규칙의 테스트도 소유한다"는 원칙에는 약점이 하나 있습니다. **한 Task가 약속한 테스트를 쓰지 않아도 `./gradlew test`는 초록색입니다.** 이 표가 그 틈을 맡습니다.

자동화하지 않았습니다. 판정 도구를 만들 수는 있지만 그 도구 자체가 검증되지 않습니다. 표를 보며 손으로 대조하고 결과를 남깁니다.

측정 시점 **112건 통과 / 실패 0**입니다.

## 두 가드는 자기가 공허하지 않은지 스스로 검사합니다

18번과 22번은 "대상이 0개여도 통과"할 수 있는 종류입니다. opt-in 가드는 패키지 필터가 어긋나면, `now()` 스캐너는 작업 디렉터리가 어긋나면 아무것도 검사하지 않고 초록불이 됩니다.

각각 짝 테스트를 뒀습니다. `guardIsNotVacuous`가 핸들러 5개 이상을, `scannerReadsSources`가 소스 파일 20개 이상을 실제로 보고 있는지 확인합니다.

## 시드와 픽스처의 대응

`sale-5`의 값이 두 곳에 있습니다. 형식이 달라 한쪽에서 다른 쪽을 생성할 수 없습니다.

| 어디 | 값 |
| --- | --- |
| `src/main/resources/data.sql` | `('sale-5', 'course-3', 60000, '2025-01-31T14:30:00Z')` |
| `SettlementFixtures.java` | `sale("sale-5", CREATOR_2, 60_000, "2025-01-31T23:30:00+09:00")` |

`2025-01-31T14:30:00Z` = `2025-01-31T23:30:00+09:00`, **같은 순간입니다.** 금액도 60,000으로 같습니다.

**시드를 바꾸면 두 곳을 다 고쳐야 합니다.** SQL 리터럴은 UTC, Java 상수는 KST 표기입니다.

## 세 상수 집합이 겹치지 않는다

| 무엇 | 어디 | 쓰는 달 |
| --- | --- | --- |
| 시드 17행 | `data.sql` | 2025-01 ~ 03 |
| 계산기 픽스처 | `SettlementFixtures.java` (package-private) | 2025-01 ~ 03 + 시드에 없는 추가 케이스 |
| E2E·API 입력 | `SettlementE2ETest`, `SaleControllerTest` 안 | **2025-06** |

Task 3의 추가 케이스(수수료 버림 33,333원, 동일 판매 다수 부분 취소)는 픽스처에만 있습니다. `data.sql`에 넣으면 creator-1의 2025-03 기대값 120,000원이 깨지는데, 그 값은 원본 과제가 명시한 숫자라 바꿀 수 없습니다.

`SettlementFixtures`는 package-private이라 Task 6이 import할 수 없고 **필요도 없습니다.** E2E는 자기 숫자(100,000 / 40,000)를 2025-06에 넣습니다.

## 이 표가 검사하지 않는 것

테스트가 **존재하는지**만 봅니다. 그 테스트가 **옳은지**는 보지 못합니다. 잘못된 기대값을 박아둔 테스트도 이 표에서는 초록색입니다. 그 층은 아래 실행 검증이 맡습니다.

## 실행 검증

로컬에서 되는 것과 평가자 환경에서 되는 것은 다릅니다. 아래는 **실제로 돌린 결과**입니다. 검수에서 나온 결함을 고친 뒤 숫자만 고치지 않고 처음부터 다시 실행했습니다.

| 항목 | 결과 |
| --- | --- |
| 새로 클론한 곳에서 `./gradlew clean test` | **112건 / 실패 0** |
| `bootRun` 기동 | `Started SettlementApplication in 2.364 seconds`, ERROR·Exception 0건 |
| `gradlew` 권한, wrapper jar 추적 | `100755 gradlew`, `100644 gradle-wrapper.jar` |
| `git status` 비어 있음, 산출물 미추적 | `build`·`.gradle`·`.claude` 추적 0건 |
| 커버리지 감사 빈 행 | 40행 전부 채움 |

응답 대조입니다. 문서의 JSON은 전부 여기서 받은 값입니다.

| 확인 | 결과 |
| --- | --- |
| creator-1 2025-03 | `payout` 120,000 |
| 운영자 2025-03 / 2025-01~03 | `totalPayout` 168,000 / **264,000** |
| 월별 3회 합 (대조군) | 252,000 — 위와 다릅니다 |
| creator-2 2025-02 | −60,000 (수수료 0) |
| 판매 목록 `sale-5` 1월 | `refundStatus` `FULL` |
| 타인 정산 403 | 6필드 + `code` |
| 405 프레임워크 실패 | `code`·`type` 없이 problem+json |
| 금액 상한 초과 | 400 `VALIDATION_FAILED` |
| 결제 이전 취소 | 409 `CANCEL_BEFORE_PAYMENT` |
| 지원 범위 밖 종료일 | 400 `INVALID_SETTLEMENT_PERIOD` (500 아님) |
| 시드 17행 | `data.sql`, `rowCounts` 일치 |

포트 8080이 점유돼 있어 `SERVER_PORT=18080`으로 띄웠습니다. 나머지는 동일합니다.

점검에서 결함이 나오면 **여기서 고치지 않고** 해당 Task로 되돌립니다. 제출 직전에 급하게 고친 코드가 테스트를 거치지 않고 들어가는 것이 가장 위험합니다.
